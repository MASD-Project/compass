One row per step a run recorded, keyed by the run and the step's =ord= in
=test.step=. It is deleted with its run.

* Flags
:PROPERTIES:
:product:    compass
:component:  db
:schema:     activity
:profile:    activity-record
:END:

The profile =activity-record= fixes =current_state= and =retained=: the table holds test activity that exists nowhere else, so a model change that drops or retypes one of its columns needs a migration in the same pull request.

The investigation's =activity-record= fixes an =identity= key; this table's
key is =(run, step_ord)=. The model states the key on its columns, which the
profile must allow.

* Columns

** run
:PROPERTIES:
:type:         bigint
:primary_key:  true
:key_kind:     natural
:END:

The run the result belongs to.

** step_ord
:PROPERTIES:
:type:         integer
:primary_key:  true
:key_kind:     natural
:END:

The step's =ord= in =test.step= of the scenario the run ran. It is a value, not a position in a vector, so its key kind is =natural=, not =ord=.

** outcome
:PROPERTIES:
:type:    text
:values:  pass fail blocked skipped
:enum:    step_outcome
:END:

The step's outcome.

** notes
:PROPERTIES:
:type:      text
:nullable:  true
:END:

What the tester wrote about the step.

* Foreign keys

** run
:PROPERTIES:
:references:  activity.run
:on_delete:   cascade
:END:

Deleting a run deletes its step results.

* C++

The generated row is =compass::db::types::step_result_row= of
=compass.db/types/step_result_row.hpp=. =:enum: step_outcome= names the enumeration of =outcome=, as
Record test campaigns named it. Nothing reads or writes it yet:
Record test campaigns writes the table with its own SQL. The profile leaves
the COPY writer off.

* Notes

=step_ord= names a step by its place in a scenario's definition without a
foreign key, since =activity= never references the corpus.
