One row per place an attachment is attached: to a run, optionally at a step,
or to a note, never both. It is deleted with its run or note; the attachment's
bytes stay until nothing names them.

* Flags
:PROPERTIES:
:product:    compass
:component:  db
:schema:     activity
:profile:    activity-record
:END:

The profile =activity-record= fixes =current_state= and =retained=: the table holds test activity that exists nowhere else, so a model change that drops or retypes one of its columns needs a migration in the same pull request.

The attachment's placement's identity. =GENERATED ALWAYS AS IDENTITY=: read back, never written.

** note

:PROPERTIES:

The =ord= of the step of the run it is attached at, if any.

** caption
:PROPERTIES:
:type:      text
:nullable:  true
:END:

The caption the tester gave it.

* Foreign keys

** attachment
:PROPERTIES:
:references:  activity.attachment
:END:

An attachment that is attached somewhere cannot be deleted.

** run
:PROPERTIES:
:references:  activity.run
:on_delete:   cascade
:END:

Deleting a run deletes what is attached to it.

** note
:PROPERTIES:
:references:  activity.note
:on_delete:   cascade
:END:

Deleting a note deletes what is attached to it.

* C++

#176 has no C++ for this table; [[id:C1DC377F-4A1B-4131-B734-FE28DB63CF03][Serve the documents]]
will need its row, reader and insert. The row the model generates is the
specification of that code.

* Notes

The check makes =run= and =note= a choice of one. A generated row carries
both as optionals; a sum type would say it better, and the model has no way
to ask for one.
