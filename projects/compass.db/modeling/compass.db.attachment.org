One row per distinct attached file, keyed by the blob ID of its bytes, so the
same screenshot attached twice is stored once. =activity.attached= says where
it is attached.

* Flags
:PROPERTIES:
:product:    compass
:component:  db
:schema:     activity
:profile:    activity-record
:END:

The profile =activity-record= fixes =current_state= and =retained=: the table holds test activity that exists nowhere else, so a model change that drops or retypes one of its columns needs a migration in the same pull request.

The investigation's =activity-record= fixes an =identity= key; this table is
keyed by a content hash. The model states the key on its column.

** bytes
:PROPERTIES:

:END:

The file's bytes.

* C++

#176 has no C++ for this table; [[id:C1DC377F-4A1B-4131-B734-FE28DB63CF03][Serve the documents]]
will need its row, reader and insert. The row the model generates is the
specification of that code.

* Notes

=bytes= is the only =bytea= column of the schema that is not a blob ID; the
model states no =cpp_type= for it and leaves the choice of byte container to
the MASD entity context.
