#+title: compass.store
#+description: The content-addressed store every worktree of a repository shares: git blob IDs as keys, taken from git's index when git would call a file clean, else from a per-worktree index of the files compass hashed, else hashed; objects and action objects in append-only packs under the git common directory, each published whole by one writer with no lock, merged geometrically so the file count stays logarithmic, and collected by rewriting them without the entries no worktree refers to; and a reader of git's own object database, loose and packed, so a commit is read with no checkout.

This page is the component overview for =compass.store=, a simple component in
the infrastructure layer of the
[[id:8A9A460F-8024-4890-B091-C0D02FD84218][System Model]].

* Summary

=compass.store= keeps what compass-ng has already computed, keyed by the
content it was computed from. The key is the ID git gives that content, so a
file with the same bytes has the same key in every worktree and its parse is
done once per repository. The store is a cache: deleting it loses speed and
nothing else. It is a handful of files whatever it holds: every object and
action object is an entry of a pack, and packs are merged as they are
written. Collection keeps it bounded: an entry no worktree refers to is
dropped, oldest first, once the store passes its cap.

Most keys cost nothing to find. Git's index already holds the ID of every
clean tracked file, so the store reads the index. A file whose index ID it
cannot trust is hashed once, and its stat data and ID go into a worktree
index of its own, so the next run finds it from stat data too.

The component knows keys, places and files. It does not know what an object
holds. The bytes of a parsed org document are laid out by
[[id:44C128E0-BCF3-4574-B171-BF5E72325085][compass.org]], in
=io/object.hpp=, which also checks them when they are mapped back. A caller
joins the two: it hashes a source, asks =compass.org= to encode the tables,
and adds the bytes to a =pack_writer=; later it finds them through a
=pack_reader=, which maps the packs with =compass.platform=, and asks
=compass.org= to decode them.

* Inputs

- The bytes of a source file, to compute its blob ID.
- The root of a git checkout, to find the store and to resolve the IDs of
  its files: its index, its configuration and its attributes files are read,
  never written, and no lock is taken. The worktree index under its git
  directory is read, and written when the caller asks.
- The bytes of an object, to write.
- The key and body of an action object, to write or read.
- The packs under the git common directory, mapped by a reader, appended
  to by a writer, merged and rewritten under the lock of the packs
  directory.
- For a commit: git's object database under the git common directory, its
  pack files, their indexes, its loose objects and the databases its
  =info/alternates= names, read, never written.
- For collection: the git directory of every worktree, read from the common
  directory; the git index and worktree index of each, read, never written;
  for each, the action keys a caller-supplied function says it names;
  every pack; a size cap and a grace period.

* Outputs

- *Blob ID.* =ops::blob_id_of= returns the SHA-1 of ="blob <size>\0<content>"=
  as 20 raw bytes, the ID =git hash-object= prints. For a clean tracked file it
  equals the ID in git's index. =ops::to_hex= prints it as git does.
  The SHA-1 block function unrolls its rounds over a ring of sixteen
  words, about 700 MB/s on a 2018 desktop core without SHA extensions;
  every record, index and cache object read is hashed, which was half the
  instructions of an edit hook.
- *Index.* =ops::parse_git_index= reads versions 2, 3 and 4 of git's index
  (gitformat-index(5)), with the path prefix compression of version 4 and
  the extended flags, into the columns of =types::git_index=: path, mode,
  stat data, blob ID, stage and intent-to-add. Optional extensions are
  skipped. A required one, such as the =link= of a split index, rejects the
  file, and so does a trailing SHA-1 that does not match, unless it is all
  zeros as =index.skipHash= writes it. =io::read_git_index= opens the file
  read-only and records its modification time.
  =io::id_resolver= treats a rejected index as no index: every file is
  hashed, and =index_problem= says why, so an unusable index costs speed and
  never correctness.
- *Clean.* =ops::is_unchanged= says whether a file is unchanged since its
  entry was recorded, from stat data alone. Every field must match,
  nanoseconds included, which is stricter than git on Linux. An entry
  modified in the second the record was written, or later, is racily clean
  (see git's racy-git documentation) and is not trusted. =ops::is_clean=,
  for git's index, also never trusts a size of zero, since git zeroes the
  size of an entry it could not prove clean.
- *Conversion.* Git's ID names the bytes after line-ending conversion and
  clean filters. =ops::read_git_config= notes =core.autocrlf=, the object
  format, =core.attributesFile= and includes; =ops::read_attributes= keeps
  the rules that set =text=, =eol=, =crlf=, =filter=, =ident= or
  =working-tree-encoding=, directly or through a macro; =ops::converts=
  matches a path against them with gitignore's pattern rules. Both err
  towards distrust: any configuration file that sets =core.autocrlf= to
  anything but false counts, every conditional include is read, and a
  pattern too odd to match exactly matches everything.
- *Resolution.* =io::id_resolver= reads the index of the checkout's own git
  directory (=io::git_dir=, which follows the =.git= file of a linked
  worktree), the system, global and repository configuration, and the
  attributes files: system, global, =info/attributes= and the
  =.gitattributes= of every directory that holds a tracked path. For a path
  it returns the ID from the index when the entry is at stage 0, is a
  regular file, was not added with intent to add, matches no conversion
  rule and is clean; otherwise it hashes the file with =io::hash_file=. A
  conflicted, untracked or racily clean path is hashed, and so is every path
  when =core.autocrlf= converts or the object format is not SHA-1, unless
  the worktree index knows it. The answer names its source (=git_index=,
  =worktree_index= or =hashed=) and carries the stat data the file had.
- *Worktree index.* =<git dir>/compass/index= (=io::worktree_index_path=),
  under the checkout's own git directory, so each linked worktree keeps its
  own. It holds path, stat data and ID of each file compass hashed; a file
  whose ID git's index gives has no entry. =ops::encode_worktree_index=
  lays it out little-endian: magic =CMPSWTI\n=, version, entry count and
  written time, then each entry in path order, then the SHA-1 of all of it.
  =ops::decode_worktree_index= rejects a file whose magic, version or
  checksum is wrong, that is cut short, or whose paths are out of order;
  the resolver then treats the index as empty and says why in
  =worktree_index_problem=. An entry is used when =ops::is_unchanged=
  holds against the written time, which is the time the resolver that
  wrote it was built, read from the coarse clock the kernel stamps files
  with. That time is no later than any hash in the file, so a file
  modified after compass hashed it is never trusted, even when the
  modification kept its stat data.
- *Index rewrite.* =id_resolver::write_worktree_index= takes the paths
  resolved in the run and their answers, keeps an entry for each that was
  not from git's index, carries over the previous entries of other paths
  whose files are still unchanged, and drops the rest, so a removed file
  loses its entry. It writes a temporary file and renames it. Two runs in
  one worktree that write at once do not corrupt the file: the last rename
  wins, and the entries of the other are hashed again on the next run.
- *Location.* =io::git_common_dir= resolves the git directory every worktree
  shares, reading =.git= and =commondir= as git writes them, with no git
  process. =io::packs_dir= is =compass/packs= under it. The first layout
  of the store, a file per object, manifest and result under
  =compass/objects=, =compass/manifests= and =compass/results=
  (=io::legacy_store_dirs=), is read by nothing; collection removes it.
- *Entries.* An entry is an object, keyed by the blob ID of its source, or
  an action object of either kind (=types::entry_kind=: =object=,
  =manifest=, =result=), keyed by the key its writer computed. An action
  object is named by a key its writer computes from what an action
  depends on, not by the hash of its bytes, so the store cannot check it
  against its name. =ops::encode_action= frames a body with the magic
  =CMPSACT\n= and a SHA-1 of the key, the magic and the body, so an
  object damaged, cut short, or copied under another key fails
  =ops::decode_action=. What a body holds is the writer's: =compass.codec=
  keeps its result cache here. An object is checked by its decoder, as
  before; the store checks neither.
- *Packs.* A pack (=ops/pack.hpp=) is one file,
  =pack-<16 hex digits of the time><16 random hex digits>.cpk=: a 16-byte
  header (magic =CMPSPAK\n=, version =ops::pack_version=), the entries,
  each at a multiple of 8 bytes so a mapped object is as aligned as a
  mapped file, then the index: a fan-out table of 256 counts by the first
  byte of the key, one 48-byte row per entry in order of key then kind
  (key, kind, offset, size, and the time the entry was first written), and
  a 32-byte footer naming the index and the entry count, ending
  =CMPSEND\n=. Integers are little-endian. =ops::parse_pack= checks the
  header, the footer, the fan-out table, the order of the rows and that
  every entry lies inside the pack, in one pass over the index; it reads
  no entry. =ops::find_entry= finds a key through the fan-out table and a
  binary search. Of two entries of one kind and key in one pack, the index
  keeps the later written.
- *Writes.* =io::pack_writer= appends each entry to a temporary file
  =tmp_<random>= in the packs directory as it is added, from any number of
  threads, and =publish= writes the index and renames the file to its
  pack name. A pack is seen whole or not at all, and no writer shares a
  file with another, so writers in any number of processes and worktrees
  need no lock. A writer destroyed unpublished removes its file. Nothing
  is synced to disk; a pack a crash cut short does not parse and is
  skipped, and an entry a crash damaged fails its decoder and is written
  again. A run writes one pack per batch: the objects it parsed, the
  results and manifests of the units it ran, the formatted files it
  formatted.
- *Repacking.* After each publish =io::repack= merges the smallest packs
  into one, as git's geometric repack does: =ops::packs_to_merge= takes
  the fewest smallest packs such that every pack left is at least twice
  the size of all the smaller ones together. So the store holds a number
  of packs logarithmic in its size, and each byte is copied a logarithmic
  number of times. Merging and collection take the lock of the packs
  directory, =lock=, with =flock=, so the kernel releases it when its
  holder dies; a repack that finds it held gives up at once and the next
  publish tries again. A merge publishes its pack before it removes the
  ones it merged, and keeps each entry's written time.
- *Reads.* =io::pack_reader= maps every pack that parses
  (=io::open_packs=). It lists the directory until two listings in a row
  agree and no listed pack vanished before it was opened, opening each
  name once, so a reader racing a merge holds either the merged packs or
  the merge's pack. After a thousand listings under constant change it
  keeps what it holds, and an entry it lacks is a miss. A pack published
  after opening is not seen; a pack removed after opening stays readable,
  since its mapping outlives the unlink. =find= returns the bytes of an
  entry, valid while the reader lives; any number of threads share a
  reader. Of a manifest, which a writer rewrites under the same key, the
  copy written last is read, whichever pack holds it; of an object or a
  result, whose key names its content, the first found.
  =read_action= decodes an action object, and when a damaged copy hides a
  sound one in another pack, it reads the sound one; a missing or damaged
  object is a miss, which its caller treats as such.
- *Leftovers.* A crash between the first entry and the rename leaves a
  file whose name starts with =tmp_=. Nothing reads it, and collection
  removes it once it is older than the grace period, as it removes a pack
  that does not parse.
- *Collection.* An object is live when a worktree of the repository refers
  to its ID, as git decides reachability; access times are never read, so
  loading an object writes nothing. =io::worktree_git_dirs= lists the git
  directory of each worktree: the common directory, which is the main
  worktree's, and each directory under =worktrees/= that holds a git index
  or a worktree index. The checkout a linked worktree names is not looked
  at, so a worktree whose checkout was deleted keeps its objects until git
  prunes it. =io::live_ids= gathers every ID those indexes name, at every
  stage. An action object is live while a worktree names its key:
  =io::collect= asks its =action_roots= function for the keys of each
  worktree, since the record that names them belongs to the component that
  wrote them. =io::collect= holds the lock, opens every pack and lists
  each entry with the time it was first written; an entry a later one of
  the same kind and key hides is superseded and always dropped.
  =ops::plan_collection= keeps the live entries and any written within
  the grace period, an hour by default, so a run in progress never loses
  an entry it just wrote; it takes the others oldest first by written
  time while the store is over its cap, and every old temporary file.
  Unless this is a dry run, the entries kept go into one new pack and the
  old packs are removed; a store of one pack with nothing to drop is left
  as it is. A pack a writer publishes during the collection is not
  touched. The directories of the first layout are removed whole, and the
  bytes the packs hold after it go to =compass/collected=
  (=io::collected_file_path=).
- *Collection as part of the runs.* =io::collect_when_grown= collects when
  the packs hold at least =io::collection_floor= (256 MB) and at least
  twice what the last collection left, or when none is recorded, with no
  cap and the default grace period. So a store is rewritten at most once
  per doubling, and a collection copies no more bytes, over time, than the
  runs wrote. It does not wait for the lock: when another process holds
  it the collection is skipped (=collection_result::skipped=) and the next
  run that finds the store grown tries again.
- *Collection is safe to run at any time.* An index that exists and cannot
  be read, split, damaged or of another version, stops the collection before
  anything is removed, since the IDs it holds cannot be kept. A process that
  has a pack mapped keeps its mapping after the unlink. A run that looks
  up a dropped object finds it missing, parses the source again and writes
  the object back, so collection costs speed and never correctness.
- *Many writers at once.* The test =many processes writing, reading,
  repacking and collecting one store at once= forks six writers, each
  publishing 25 packs of 41 results and a manifest and reading back
  everything it wrote after each publish, two readers that check every
  entry they find, and a collector rewriting the store in a loop. Every
  one of the 6,000 results is read back whole, no temporary file is left,
  and after a repack the store holds at most 12 packs. Removing the merged
  packs before publishing the merge loses entries in it every time.
- *The first layout.* A store in the first layout is not read: an
  install of this layout starts cold. The new build changes the code hash
  of every codec, so its results would miss anyway, and only the parsed
  objects, about half a second of parsing on ORE Studio, could be reused;
  converting them is not worth the code. =compass gc= removes the old
  directories, and until then they cost files and nothing else.

SHA-1 is implemented here, in about a hundred lines, rather than taken from
OpenSSL. The store hashes only files whose ID git's index does not already
hold, so the speed of an accelerated SHA-1 buys little, and OpenSSL would be
the largest dependency of the build for one function. The same SHA-1 checks
the trailing checksum of the index; on ORE Studio's 9 MB index that is about
29 ms of the 65 ms it takes to build a resolver.

On a copy of ORE Studio at =545cafca45= (10,929 org documents), with the
store and records cleared, =compass check= with every gate enabled, on 8
cores at load 52 to 66, left this in =compass/=:

| Layout | Files | Bytes (apparent) | Bytes on disk | Cold | Warm (3 runs) | Hook |
|--------+-------+------------------+---------------+------+---------------+------|
| one file each (=68833c3=) | 166,836 | 889 MB | 1,471 MB | 64.4 s | 4.6, 5.4, 5.6 s | 0.43 to 0.66 s |
| packs | 6 (one pack, its lock and four records) | 898 MB | 898 MB | 68.0 s | 4.5, 5.1, 5.8 s | 0.56 to 0.75 s |

The packs hold 620 MB, the 166,832 entries the files held. The files'
apparent size was 612 MB, but each took at least one 4 KiB block, so they
took 1,194 MB on disk. The cold run is mostly clang-format; the times
differ by less than the noise of a machine at that load. A warm check read
all 10,929 objects from the pack, and its findings were the cold run's.
=compass gc= then took 1.3 s and removed nothing; with =--grace 0= it
dropped 22,959 entries (180 MB) that no record names, the formatted files,
and the next check formatted them again in 50 s.

On ORE Studio's live worktree (60,047 tracked files),
=compass-bench ids --repeat 5 --verify 500= took 57,283 IDs (95.4%) from
the index and hashed 2,764 files (74.7 MB), all of them sent to hashing by
=.gitattributes= rules that set =text= or =eol=. The median repetition took
65 ms to build the resolver, 31 ms to stat every file and 75 ms to hash, on
8 threads of a shared machine, so the numbers are indicative. Every one of
the 60,047 IDs matched =git hash-object= in a =--verify all= run.

On a repository made from an archive of ORE Studio =origin/main= at
=a04ad2a5c3= (60,213 files, 10,910 of them org),
=compass-bench warm --repeat 5= after one cold run took 10,898 org IDs from
git's index and 12 from the worktree index, hashed none, loaded and checked
all 10,910 objects and wrote none. The median warm repetition took 210 ms:
115 ms to build the resolver and resolve every ID, 86 ms to load, 2 ms in
the empty write phase and 2 ms to rewrite the worktree index, against a
budget of one second. Listing the files with =git ls-files= and =lstat=
took another 120 ms outside the stage. The cold run took 399 ms, 289 ms of
it parsing and writing. Load average was 7 to 10 on 8 cores. A
=compass-bench ids --verify all= run on the same repository afterwards
matched all 60,213 IDs, the 12 from the worktree index among them.

On the same kind of repository, an archive of ORE Studio =origin/main= at
=7aa4435e21= (60,498 files, 10,917 org) with a linked worktree whose index
had held 1,000 edited org files and was reset, =compass-bench gc= at
=433b57a= found 2 worktrees, 59,431 live IDs and 11,915 objects (69.4 MB):
10,915 live (66.2 MB) and 1,000 unreferenced (3.3 MB). With the default
grace of an hour all 1,000 were within it and nothing was chosen; with
=--grace 0= and a cap half way between, 517 objects (1.6 MB) were removed,
oldest first, and a second run removed none. A collection took about
150 ms: 113 to 123 ms to read both git indexes, which is mostly their
checksums, 30 ms to stat the store, 1.5 ms to plan and 3 ms to unlink.
Warm runs afterwards loaded all 10,917 objects of the main worktree and
wrote none; restoring the edits in the linked worktree parsed and wrote the
517 removed objects and loaded the other 10,400. The machine was shared, so
the numbers are indicative.

On a copy of ORE Studio at =08a73b6767= whose objects =git gc= had put in
one 613 MB pack, listing the commit's 60,552 paths took 32 ms. Reading
all of their blobs, 1,619 MB, took 3.7 s on one thread and 0.83 s on 8;
=git cat-file --batch= read the same blobs in 4.0 s. Reading the 10,928
org blobs, 70 MB, took 250 ms on one thread and 34 ms on 8. The machine
was shared, so the numbers are indicative.

* Dependencies

- The C++23 standard library.
- =compass.platform=, the foundation layer, for =mapped_file=: the git
  object reader maps packs, their indexes and loose objects.
- zlib, from its vcpkg port, to inflate git's objects.
- POSIX (=open=, =fstat=, =lstat=, =read=, =write=, =rename=, =unlink=,
  =flock=, =clock_gettime=), and Linux's =CLOCK_REALTIME_COARSE=.
- Catch2 and the =git= command, for the tests only. The store itself starts
  no git process.
