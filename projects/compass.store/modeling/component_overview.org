#+title: compass.store
#+description: The content-addressed store every worktree of a repository shares: git blob IDs as keys, taken from git's index when git would call a file clean, else from a per-worktree index of the files compass hashed, else hashed; object paths under the git common directory, action objects named by a key their writer computes, writes that land whole or not at all, and collection of the objects and action objects no worktree refers to.

This page is the component overview for =compass.store=, a simple component in
the infrastructure layer of the
[[id:8A9A460F-8024-4890-B091-C0D02FD84218][System Model]].

* Summary

=compass.store= keeps what compass-ng has already computed, keyed by the
content it was computed from. The key is the ID git gives that content, so a
file with the same bytes has the same key in every worktree and its parse is
done once per repository. The store is a cache: deleting it loses speed and
nothing else. Collection keeps it bounded: an object no worktree refers to
is removed, oldest first, once the store passes its cap.

Most keys cost nothing to find. Git's index already holds the ID of every
clean tracked file, so the store reads the index. A file whose index ID it
cannot trust is hashed once, and its stat data and ID go into a worktree
index of its own, so the next run finds it from stat data too.

The component knows keys, places and files. It does not know what an object
holds. The bytes of a parsed org document are laid out by
[[id:44C128E0-BCF3-4574-B171-BF5E72325085][compass.org]], in
=io/object.hpp=, which also checks them when they are mapped back. A caller
joins the two: it hashes a source, asks =compass.org= to encode the tables,
and hands the bytes to =write_object=; later it maps the file with
=compass.platform= and asks =compass.org= to decode it.

* Inputs

- The bytes of a source file, to compute its blob ID.
- The root of a git checkout, to find the store and to resolve the IDs of
  its files: its index, its configuration and its attributes files are read,
  never written, and no lock is taken. The worktree index under its git
  directory is read, and written when the caller asks.
- The bytes of an object, to write.
- The key and body of an action object, to write or read.
- For collection: the git directory of every worktree, read from the common
  directory; the git index and worktree index of each, read, never written;
  for each, the action keys a caller-supplied function says it names; the
  objects and action directories, listed; a size cap and a grace period.

* Outputs

- *Blob ID.* =ops::blob_id_of= returns the SHA-1 of ="blob <size>\0<content>"=
  as 20 raw bytes, the ID =git hash-object= prints. For a clean tracked file it
  equals the ID in git's index. =ops::to_hex= prints it as git does.
- *Index.* =ops::parse_git_index= reads versions 2, 3 and 4 of git's index
  (gitformat-index(5)), with the path prefix compression of version 4 and
  the extended flags, into the columns of =types::git_index=: path, mode,
  stat data, blob ID, stage and intent-to-add. Optional extensions are
  skipped. A required one, such as the =link= of a split index, rejects the
  file, and so does a trailing SHA-1 that does not match, unless it is all
  zeros as =index.skipHash= writes it. =io::read_git_index= opens the file
  read-only and records its modification time.
  =io::id_resolver= treats a rejected index as no index: every file is
  hashed, and =index_problem= says why, so an unusable index costs speed and
  never correctness.
- *Clean.* =ops::is_unchanged= says whether a file is unchanged since its
  entry was recorded, from stat data alone. Every field must match,
  nanoseconds included, which is stricter than git on Linux. An entry
  modified in the second the record was written, or later, is racily clean
  (see git's racy-git documentation) and is not trusted. =ops::is_clean=,
  for git's index, also never trusts a size of zero, since git zeroes the
  size of an entry it could not prove clean.
- *Conversion.* Git's ID names the bytes after line-ending conversion and
  clean filters. =ops::read_git_config= notes =core.autocrlf=, the object
  format, =core.attributesFile= and includes; =ops::read_attributes= keeps
  the rules that set =text=, =eol=, =crlf=, =filter=, =ident= or
  =working-tree-encoding=, directly or through a macro; =ops::converts=
  matches a path against them with gitignore's pattern rules. Both err
  towards distrust: any configuration file that sets =core.autocrlf= to
  anything but false counts, every conditional include is read, and a
  pattern too odd to match exactly matches everything.
- *Resolution.* =io::id_resolver= reads the index of the checkout's own git
  directory (=io::git_dir=, which follows the =.git= file of a linked
  worktree), the system, global and repository configuration, and the
  attributes files: system, global, =info/attributes= and the
  =.gitattributes= of every directory that holds a tracked path. For a path
  it returns the ID from the index when the entry is at stage 0, is a
  regular file, was not added with intent to add, matches no conversion
  rule and is clean; otherwise it hashes the file with =io::hash_file=. A
  conflicted, untracked or racily clean path is hashed, and so is every path
  when =core.autocrlf= converts or the object format is not SHA-1, unless
  the worktree index knows it. The answer names its source (=git_index=,
  =worktree_index= or =hashed=) and carries the stat data the file had.
- *Worktree index.* =<git dir>/compass/index= (=io::worktree_index_path=),
  under the checkout's own git directory, so each linked worktree keeps its
  own. It holds path, stat data and ID of each file compass hashed; a file
  whose ID git's index gives has no entry. =ops::encode_worktree_index=
  lays it out little-endian: magic =CMPSWTI\n=, version, entry count and
  written time, then each entry in path order, then the SHA-1 of all of it.
  =ops::decode_worktree_index= rejects a file whose magic, version or
  checksum is wrong, that is cut short, or whose paths are out of order;
  the resolver then treats the index as empty and says why in
  =worktree_index_problem=. An entry is used when =ops::is_unchanged=
  holds against the written time, which is the time the resolver that
  wrote it was built, read from the coarse clock the kernel stamps files
  with. That time is no later than any hash in the file, so a file
  modified after compass hashed it is never trusted, even when the
  modification kept its stat data.
- *Index rewrite.* =id_resolver::write_worktree_index= takes the paths
  resolved in the run and their answers, keeps an entry for each that was
  not from git's index, carries over the previous entries of other paths
  whose files are still unchanged, and drops the rest, so a removed file
  loses its entry. It writes a temporary file and renames it. Two runs in
  one worktree that write at once do not corrupt the file: the last rename
  wins, and the entries of the other are hashed again on the next run.
- *Location.* =io::git_common_dir= resolves the git directory every worktree
  shares, reading =.git= and =commondir= as git writes them, with no git
  process. =io::objects_dir= is =compass/objects= under it. =io::object_path=
  is =<first two hex digits>/<other 38>= under that, the layout of git's loose
  objects.
- *Writes.* =io::write_object= writes to a temporary file in the directory of
  the object and renames it into place; the worktree index is written the
  same way. A reader sees the old object, the new
  one or none. Concurrent writers of one object all succeed and leave one
  file. Nothing is synced to disk; an object a crash cut short fails the
  checks of its decoder and is written again.
- *Reads.* An object is read by mapping its file with =mapped_file=. A missing
  file is a miss.
- *Action objects.* An action object is named by a key its writer computes
  from what an action depends on, not by the hash of its bytes, so the store
  cannot check it against its name. =types::action_kind= has two kinds, each
  in its own directory under the git common directory: =compass/manifests=
  and =compass/results= (=io::actions_dir=), laid out as objects are.
  =ops::encode_action= frames a body with the magic =CMPSACT\n= and a SHA-1
  of the key, the magic and the body, so an object damaged, cut short, or
  copied under another key fails =ops::decode_action=. =io::write_action=
  writes through =write_object=; =io::read_action= returns the body, or
  nothing for a missing or damaged object, which its caller treats as a
  miss. What a body holds is the writer's: =compass.codec= keeps its result
  cache here.
- *Leftovers.* A crash between write and rename leaves a file whose name
  starts with =tmp_=. Nothing reads it, and collection removes it once it is
  older than the grace period.
- *Collection.* An object is live when a worktree of the repository refers
  to its ID, as git decides reachability; access times are never read, so
  loading an object writes nothing. =io::worktree_git_dirs= lists the git
  directory of each worktree: the common directory, which is the main
  worktree's, and each directory under =worktrees/= that holds a git index
  or a worktree index. The checkout a linked worktree names is not looked
  at, so a worktree whose checkout was deleted keeps its objects until git
  prunes it. =io::live_ids= gathers every ID those indexes name, at every
  stage. An action object is live while a worktree names its key:
  =io::collect= asks its =action_roots= function for the keys of each
  worktree, since the record that names them belongs to the component that
  wrote them. =io::list_objects= stats each object and temporary file, of
  the objects directory and of both action directories, and the plan treats
  them as one store under one cap and grace period.
  =ops::plan_collection= keeps the live objects and any file modified within
  the grace period, an hour by default, so a run in progress never loses an
  object it just wrote; it takes the other objects oldest first by
  modification time while the store is over its cap, and every old
  temporary file. =io::collect= runs the four and unlinks each victim whose
  size and modification time are still the ones listed; a dry run unlinks
  nothing.
- *Collection is safe to run at any time.* An index that exists and cannot
  be read, split, damaged or of another version, stops the collection before
  anything is removed, since the IDs it holds cannot be kept. A process that
  has an object mapped keeps its mapping after the unlink. A run that looks
  up a removed object finds it missing, parses the source again and writes
  the object back, so collection costs speed and never correctness.

SHA-1 is implemented here, in about a hundred lines, rather than taken from
OpenSSL. The store hashes only files whose ID git's index does not already
hold, so the speed of an accelerated SHA-1 buys little, and OpenSSL would be
the largest dependency of the build for one function. The same SHA-1 checks
the trailing checksum of the index; on ORE Studio's 9 MB index that is about
29 ms of the 65 ms it takes to build a resolver.

On ORE Studio's live worktree (60,047 tracked files),
=compass-bench ids --repeat 5 --verify 500= took 57,283 IDs (95.4%) from
the index and hashed 2,764 files (74.7 MB), all of them sent to hashing by
=.gitattributes= rules that set =text= or =eol=. The median repetition took
65 ms to build the resolver, 31 ms to stat every file and 75 ms to hash, on
8 threads of a shared machine, so the numbers are indicative. Every one of
the 60,047 IDs matched =git hash-object= in a =--verify all= run.

On a repository made from an archive of ORE Studio =origin/main= at
=a04ad2a5c3= (60,213 files, 10,910 of them org),
=compass-bench warm --repeat 5= after one cold run took 10,898 org IDs from
git's index and 12 from the worktree index, hashed none, loaded and checked
all 10,910 objects and wrote none. The median warm repetition took 210 ms:
115 ms to build the resolver and resolve every ID, 86 ms to load, 2 ms in
the empty write phase and 2 ms to rewrite the worktree index, against a
budget of one second. Listing the files with =git ls-files= and =lstat=
took another 120 ms outside the stage. The cold run took 399 ms, 289 ms of
it parsing and writing. Load average was 7 to 10 on 8 cores. A
=compass-bench ids --verify all= run on the same repository afterwards
matched all 60,213 IDs, the 12 from the worktree index among them.

On the same kind of repository, an archive of ORE Studio =origin/main= at
=7aa4435e21= (60,498 files, 10,917 org) with a linked worktree whose index
had held 1,000 edited org files and was reset, =compass-bench gc= at
=433b57a= found 2 worktrees, 59,431 live IDs and 11,915 objects (69.4 MB):
10,915 live (66.2 MB) and 1,000 unreferenced (3.3 MB). With the default
grace of an hour all 1,000 were within it and nothing was chosen; with
=--grace 0= and a cap half way between, 517 objects (1.6 MB) were removed,
oldest first, and a second run removed none. A collection took about
150 ms: 113 to 123 ms to read both git indexes, which is mostly their
checksums, 30 ms to stat the store, 1.5 ms to plan and 3 ms to unlink.
Warm runs afterwards loaded all 10,917 objects of the main worktree and
wrote none; restoring the edits in the linked worktree parsed and wrote the
517 removed objects and loaded the other 10,400. The machine was shared, so
the numbers are indicative.

* Dependencies

- The C++23 standard library. No other compass-ng component.
- POSIX (=open=, =fstat=, =lstat=, =read=, =unlink=, =clock_gettime=), and
  Linux's =CLOCK_REALTIME_COARSE=.
- Catch2 and the =git= command, for the tests only. The store itself starts
  no git process.
