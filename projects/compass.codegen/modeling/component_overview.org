This page is the component overview for =compass.codegen=, a simple component
in the domain layer of the
[[id:8A9A460F-8024-4890-B091-C0D02FD84218][System Model]].

* Summary

=compass.codegen= renders ORE Studio's codegen templates in process, to the
bytes ores.codegen writes before clang-format and prettier run. ores.codegen
renders with pystache, so the engine has pystache's semantics, not the
Mustache spec's where the two differ. A template is parsed once into a flat
table of nodes and rendered as often as there are outputs.

A render has two inputs: the compiled template and a context. The context is
a tree of =compass.model= values, the same tables a model loads into, so a
model renders without being converted. Building the context ores.codegen
builds for an output is most of the work of code generation: the engine is
complete, the contexts are not. The ones built today are those of component
models, of the asset class and outcome catalogues and of the service
registry.

=build/scripts/codegen_render_dump.py= is the oracle. It runs
ores.codegen's =regenerate --all= with the formatters patched out and
captures, per output, the text it writes and the context it rendered from.

The =codegen= codec runs the whole of =regenerate --all= in the codec
runtime of =compass.codec=, and generates the service registry besides,
which no catalogue entry reaches and ores.codegen renders only through
=generate --model=, so that a hand edit to one of its outputs shows as
drift: =compass generate= writes, =compass diff= shows
and a later run reuses what it produced while none of its inputs changed.
Where the library is and which programs format the outputs are options of
the codec, set in the checkout's =.compass.org=.

* Inputs

- The options of the =codegen= codec: =library=, the directory of
  ores.codegen's library (=projects/ores.codegen/library= in ORE Studio);
  =convention_component=, the component of the catalogue whose modeling
  directory declares the convention families (=refdata=, which
  =convention_family_registry.py= names); =year=, the copyright year,
  required (=ops::copyright_year=): the year is configuration and never
  the clock, so a warm and a cold run write the same bytes in any year,
  and a new year is one change to the configuration, which reruns every
  unit; =clang_format= and =prettier=, each a
  comma-separated list of candidate programs, a name searched on =PATH= and
  a path relative to the checkout, empty for none; and
  =clang_format_style= and =prettier_style=, their style files.
- The =.mustache= files of the library's =templates/= directory.
- The =ores.*.org= node documents of the same directory, whose =#+= header
  keywords state the physical-space graph: facets, archetypes, their model
  types, component kinds, defaults and output patterns, and the template
  each archetype tangles.
- =library/data/licence-GPL-v3.txt= and =library/data/modeline.org=, which
  every context starts from, and =library/component_catalogue.org=, whose
  modeling directories say which models =regenerate --all= visits. Every
  =ores.codegen.service_registry= model of a =modeling/= directory under
  =projects/= is generated too.
- The models, as =compass.model= loads them, and each model document's
  file-level drawer, whose =:ores.<address>.enabled:= entries override the
  graph's defaults.

* Outputs

- *Compiled template.* =types::compiled_template= holds the source and one
  row per node: text, escaped or literal interpolation, section, inverted
  section or partial, with the source range of its text or name and the end
  of its body. Comments and delimiter changes leave no node.
- *Render.* =ops::render= appends a template rendered against a context
  stack. Names resolve as pystache's =ContextStack.get= resolves them,
  values render as Python's =str()=, a section repeats over a list and
  pushes any other true value, and an empty object is false. The stack may
  mix tables, so values that shadow some keys of a context for one render
  need no copy of it.
- *Output.* =ops::render_output= is =core.render_template= followed by
  =_substitute_paste_markers=: the generated-file marker after the licence
  of the template's language, =cpp_value_init= on the fields of the four
  member-declaring templates, no escaping, the org marker after an org
  output's drawer, and the =<<paste:UUID>>= blocks of the model.
- *Contexts.* =ops::library_values= builds the licence and modeline values;
  =ops::model_context= adds a model and what =generate_from_model= derives
  for its type; for the service registry, each service's SQL literals,
  image code, account variable and component, and the services with a
  psql variable under =service_registry_db_services=. The steps of an entity's context are public one by one
  (=entity_steps.hpp=), and =ops::flag_junction_columns= gives a
  junction's columns and sides their type flags, so a check can run the
  steps that read no other model without building the whole context.
- *Graph and units.* =ops::load_physical_space= reads the graph;
  =ops::model_units= lists a model's outputs as =resolve_targets= does.
  =ops::archetype_enabled= says, without the graph, whether one archetype
  of a facet both enable by default renders for a model's overrides,
  which =compass.crosscheck= asks of a model's create script, repository
  row and table writer.
  =ops::read_component_catalogue= and =ops::regenerated_models= give the
  models =regenerate --all= visits.
- *Generation.* =ops::checkout_reader= is everything generation reads of a
  checkout: documents by path, file listings by prefix and suffix, file
  bytes and whether a file exists. =ops::prepare_generation= reads what
  every model's generation shares, an =ops::generation=: the library's
  licence and modeline, the physical-space graph, the entity and checkout
  registries, the compiled templates and the models =regenerate --all=
  visits with the service registries, in order. =ops::generate_model= generates one of those models:
  it loads the model, builds its context and renders its outputs in the
  order its units name them, and throws when the model does not load,
  since a codec that emits files cannot report findings.
  =ops::plan_generation= plans every model into one table, a path two
  models name rendered from the later, and =ops::render_planned= renders
  one planned output; =compass.bench= times generation with them.
- *Facts.* What a model's generation depends on besides the documents and
  files it reads itself is a set of /facts/, each a name and the SHA-1 of
  a value: =library= (the licence, the modeline and the year), =graph=
  (every node of the physical-space graph), one per template
  (=ops::template_fact=) and those of the registries.
  =types::entity_registry= and =types::checkout_registry= hold
  =types::recorded= collections: a lookup by key records the fact of that
  element, found or not, anything that sees every element records the
  fact of the whole collection, and a copy shares the elements and
  records to its own =types::fact_reads=. A model so depends on the
  elements it looked up: the table a foreign key names, the directory it
  is in, the shell units of its component. =ops::publish_facts= gives one
  fact per element and one per collection; the value of a fact is every
  field of what it names, bound field by field, so a field added to a
  registry type does not compile until the fact includes it.
- *Codec.* =codecs::codegen= is a staged codec over every document, off by
  default. Its prepare step is =ops::prepare_generation=: it lists the
  models as the parts and publishes the facts. Each model is a part,
  generated by =ops::generate_model= through =codecs::reader_of=, which
  reads through the codec's view, so the part records each document it
  looks up, each listing and each domain header whose existence an
  entity's includes depend on, and the facts it read. An edit to a model
  generates that model and the models that read it or a fact it changes;
  an edit to a document nothing read, or to a source file, generates
  nothing. When the only inputs of a model that changed are templates,
  the model renders the outputs of those templates and keeps the others
  as its last generation left them, without building their contexts. A
  path two models name is the later model's, as the later write wins on
  disk: every entity and junction of a component names its shell
  aggregator, 78 models for =trading_commands.hpp= in ORE Studio.

  On ORE Studio at =545cafca45= (825 models, 26,212 outputs, 193 MB)
  preparing takes about 140 ms and generating every model about 2.3 s of
  processor time, 1.6 s on eight cores. An edit to an entity model
  generates 6 models; a column renamed in =party= 50; an edit to the
  template of every entity's header 573, one output each. Twelve edits
  (a renamed column, singular and field-group field, a template line, a
  model added and removed, a convention family, a component brief, the
  custom types, a graph node, the licence) gave, generated from the
  record of the clean checkout, the diff against the disk that a
  generation of every model gave.

  =codecs::settings_of= parses the options and
  =codecs::formatters_of= gives ores.codegen's formatter table:
  clang-format twice over =.cpp=, =.hpp=, =.h=, =.cxx= and =.cc= with
  =-i --style=file:{style}=, and prettier once over =.ts= and =.tsx= with
  =--write --log-level warn --config {style}=, as generate.py's
  =clang_format_files= and =prettier_format_files= run them. The runtime
  formats the codec's files through the result cache in every run.
- *=component_files=.* ORE Studio's =cmake-sources= generator
  (=regenerate_cmake_component_files.py --all=), off by default. Its
  options are =library= and =year=, which, as for =codegen=, is required
  and never the clock. A corpus
  codec that reads no document: each =projects/**/modeling/component_overview.org=
  with a =#+full_name:= line is a component, the later path winning a
  shared name. For its =src= and =tests= directories that hold a
  =CMakeLists.txt= it renders =cmake_component_files_<dir>.mustache=
  through =ops::render_output= from the library values, with
  =component.files= the =.cpp= files under the directory and
  =component.headers= the =.hpp= files under =include/=, both sorted and
  relative. It writes all 202 lists of ORE Studio =545cafca45= as the
  script does; the listing is the checkout's, so a file deleted from disk
  but still in the index is listed until =git rm=.
- *=pending_models=.* ORE Studio's =pending-models= generator, ported
  from =derive_pending_models.py= and =codegen.pending_change=, off by
  default. For each model under =projects/*/modeling/ores.*.org= whose
  first Flags section sets =:gated:= or =:pending_change:= true, it writes
  =ores.<component>.<singular>_change.org= beside it as the script derived
  it, its =:ID:= the uuid5 =ops::uuid5= gives. Since version 2 the pending
  model's =#+description:= and its "Do not edit" line name =compass
  generate= instead of the script, so ORE Studio can delete the script. A
  model the derivation refuses is refused, as a =refused= finding on its
  pending model that names the model and the reason; the other models are
  still written, and the codec removes none of the files it wrote before.

=codecs= is a local facet, as in =compass.codec=: it holds the codec, one
descriptor.

The codec scaffolds a component as it generates any other model: a
component overview is a component model, and the archetypes of a facet
serving =component= whose =#+component_kind:= lists the overview's kind
write its files. =tests/codecs_component_scaffold_tests.cpp= runs it
over a library modelled on ORE Studio's =ores.cpp.component=,
=ores.cpp.scaffold= and =ores.cpp.service-app= facets, the port of
=ores.codegen='s =tests/component_scaffold/verify.py=: a flat component,
a composite one whose group writes nothing and whose api, core and
service parts write their file sets, a component that does not opt into
the scaffold, and a part with =#+hidden_visibility: true= whose stub
header exports its function, which =exported_types= then accepts.

=compass-bench render <checkout> --out <dir>= runs the codec's generation
code on the checkout read from disk, with the options its =.compass.org=
gives; with =--oracle <dump>= it renders the dump's outputs from the dump's
contexts. =build/scripts/codegen_render_diff.py= compares
either with the oracle, output by output and template by template.

* Dependencies

- =compass.model= for the value tables contexts are made of, and the JSON
  reader for the oracle's contexts and the spec suite.
- =compass.platform= for the regular expression that finds a component's
  full name.
- =compass.codec= for the descriptor, the corpus view the codec reads
  through, the file table it emits, the formatter type and =find_program=.
- =compass.ingest=, for the tests only: the codec's tests parse a small
  checkout.
- =compass.cpp=, privately, for the Python text helpers =pending_models=
  uses. The tests also run its =exported_types= codec over a scaffolded
  part.
- The C++23 standard library.
- Catch2, for the tests only. The tests run the required files of the
  Mustache spec, expecting pystache's output for the three cases
  =build/scripts/mustache_spec_deviations.py= records where pystache
  renders =None= for a null.
