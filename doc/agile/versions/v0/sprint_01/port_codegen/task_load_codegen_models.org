* Acceptance

- All 948 ORE Studio models load, with the same model data that ores.codegen builds.

* Plan

- ores.codegen is the oracle. A small Python script, run against an ORE Studio
  archive with ORE Studio's own codegen environment, loads every model through
  =ores.codegen='s loader and dumps each as canonical JSON (sorted keys, one
  file per model). It reads ORE Studio and writes only to scratch.
- compass loads the same models from the parsed =compass.org= tables into
  data-oriented model tables in a new component, and dumps them in the same
  JSON shape.
- A differential runner compares the two dumps model by model and reports
  identical models, and per field the count of first differences, as the org
  parser's differential did. Model types and fields are added in order of how
  many models use them.
- Models read JSON payloads through =#+data_source:=; those are inputs like
  any other file and are recorded as reads.
- =compass-bench models <checkout>= loads every model and reports time; the
  ORE Studio Python loader's time for the same set is the baseline.

* Result

- =compass.model= loads ORE Studio's codegen models from the =compass.org=
  tables. The oracle is =ores.codegen='s own =core.load_model=, the one entry
  point generation uses; =codegen_model_dump.py= dumps its models as canonical
  JSON and =codegen_model_diff.py= compares them with compass's.
- 839 of 844 models are identical. The 4 family models and the trade type
  catalogue need other entity models of their directory and are refused, not
  approximated; the Load family and trade type models task finishes them.
- A model is a generic value tree in rows with handles, because the templates
  consume dictionary trees. The outline mixes the =compass.org= tables with
  =parse_org='s line rules where they disagree with org-element, so documents
  outside ORE Studio's could load differently.
- Loading is about 4 times faster than the Python loader in one process; line
  splitting is the next cheap win (about 15% of instructions).
