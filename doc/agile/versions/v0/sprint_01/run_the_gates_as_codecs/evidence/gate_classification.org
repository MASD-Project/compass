A point-in-time record, written while the story that commissioned it was open, of an [[id:A7F8D9E2-3C4B-4A5D-B67C-8E9F0A1B2C3D][investigation]] into which of ORE Studio's gates compass should port, which diff mode replaces, and which stay build gates. It is evidence for the [[id:9CBCFC60-6AA4-40A7-A6B3-7DB43ED18A42][Classify the gates]] task and was written on 2026-11-16.

It is a snapshot, not a description of the system. It builds on the gate
census in [[id:AA2CA7E4-6B27-4771-9F74-F2EEC15D902E][Investigation: ORE Studio codegen and gates]].

* Method

- Source: =git archive= of ORE Studio =origin/main= at
  =545cafca4545dfe3c9fa353429f797338c839bb1= (2026-11-16, PR #4788), extracted
  into a scratch directory on tmpfs. No ORE Studio worktree was changed.
- The copy was made a one-commit git repository so the gates that call =git
  diff= work. =vcpkg/ports= was copied from a worktree at the same submodule
  commit (=ec48c11eae=), because =git archive= leaves submodules out. Fresh
  venvs were built from =projects/ores.codegen/requirements.txt= and
  =projects/ores.compass/requirements.txt=.
- The catalogue was read from =local_checks.py= by importing it, not by hand:
  96 checks. Workflows were read from =.github/workflows/= (32 files). A
  workflow step that runs a local check shares that check's row, and the
  Source column names both. Gates only CI runs get rows of their own.
- Every check that needs no build, database or services was run one at a
  time, in catalogue order, by a script that records wall time, the CPU time
  of the whole process tree (=wait4=), the 1-minute load average just before
  it started, and the exit code. The tree was reset to =HEAD= after each one.
  Every Python interpreter ran with =-I=; a launcher put back only the
  script's own directory on =sys.path=. Wall times have a 0.05 s resolution.
- ={base}= was =HEAD=, so =site-page= and =format= saw no changed file and
  their times are those of a no-op. =component-drift --changed= still rendered
  every component.
- Build, database and test gates were not run. Their times come from CI step
  durations (=gh run view --json jobs= on the latest successful run of each
  workflow, read on 2026-11-16) and from ORE Studio's own =local_checks= reports
  (=build/output/local_checks/*.json= in =ores_dev_brave_hopper=, written on
  2026-10-18, bases =691b3d55df= and =e6eeec37b5=). The Time from column says
  which.

*The machine was loaded.* It has 8 cores. The load average was 9 to 12 for the
first half of the run, partly because an ORE Studio =compass check= ran in
another worktree at the same time, and 2.4 to 7 for the second half. The Load
column gives the figure for each gate. CPU seconds compare more fairly than
wall seconds. The investigation measured =exported-types= at 200 s and
=sql-hygiene= at 160 s at a load of 48; here they took 62 s and 50 s.

* Classes

- port :: compass reimplements the gate as a check over its loaded
  documents and sources. "Generator" in the notes marks a gate that
  regenerates an artefact compass does not yet produce and compares it; it
  becomes diff mode once compass has a codec for it.
- replace by diff mode :: the gate renders ores.codegen output and compares
  it with the tree. compass's codegen codec already produces all 26,212 of
  those outputs byte for byte, so =compass generate= in diff mode replaces the
  gate with no new check.
- keep as build gate :: the gate needs a compiler, a build tree, a database,
  services, a toolchain compass does not drive, or it is not a gate on the
  tree at all. These stay outside compass.

379 s wall and 372 s CPU. 15 gates take 335 s of that. 58 gates take under

=validate-sql-schema= runs it again after the ER parser. Without the second
run the ports take about 329 s.

=convention-kind-terms=, =ore-element-map=, =core-link-edges=), so their times
understate a passing run. Each finished in 0.2 s or less.

** Gates that do not fit the three classes

- Tool test suites: =codegen-tests=, =build-script-tests=, =compass-tests=,
  =conventions-generator-tests=, =dsh-environment= and the =compass verb
  exists= step. They test ORE Studio's own tools, not the tree. They are
  listed as keep, but each retires with the tool it tests rather than moving
  to a build tier.
- Self-tests of a check: =shell-menus --self-test= and =portable-stop
  --self-test=. They prove a check fails on a planted defect. They are listed
  as port because compass's equivalent is proving each check on past commits.
- Fixers, not gates: =nightly-format= and =nightly-includes= rewrite the tree
  and open a pull request.
- Not gates at all: =stale= and =claude= (repository bots), =build-site
  deploy= (publishing), =ci-image= (infrastructure), and
  =unity-batch-measurement= and =ore-engine-windows= (manual runs).
- Generator ports: 28 of the 87 ports regenerate an artefact other than
  ores.codegen output and compare it (tangled scripts, skill tables, seed SQL,
  =component_files.cmake=, PlantUML, inventories). They are listed as port,
  but each becomes diff mode once compass has a codec that writes the
  artefact.

** Classifications I was unsure of

- =tangle-templates=, =tangle-shell=, =tangle-http=: port only if compass
  tangles org-babel blocks exactly as Emacs does. Otherwise they stay with
  Emacs as a build-time step.
- =site-page=: listed as keep because it runs the Emacs site exporter. If
  compass's HTML codec replaces that exporter, it becomes diff mode.
- =format=: listed as port because compass already drives clang-format for
  the codec. It needs the clang-format binary, like a build gate.
- =entity-binary-types=, =generated-column-refs=, =protocol-twins=: they read
  generated output for facts the models state. Each could be a model rule
  instead, which is cheaper and does not need the generated tree.
- =xml-benchmark-recorded=: it reads git history, so its port depends on the
  Check a past commit task. It fails in the one-commit scratch repository.
- =web=: listed as keep because it needs =npm ci=. Its prettier and type check
  parts could move to a fast tier if compass gains a TypeScript reader.

** Measurement caveats

- The load average was 9 to 12 on 8 cores for the first 31 gates, partly
  from an ORE Studio =compass check= in another worktree, and 2.4 to 7 later.
  Wall times early in the run are inflated. CPU times are fairer.
- =component-drift= was run with =--base HEAD=, and it still rendered every
  component. Its ORE reports give 188 to 737 s for real changes.
- =site-page= and =format= saw no changed files, so their times are those of
  a no-op.
- Ten local gates and two CI gates exit non-zero here. Eleven reflect ORE at
  this commit: the 24 known drift files in two of the diff-mode gates, a tangle
  difference in =tangle-shell=, a stale PlantUML file, a stale backlog index,
  the shared =r.id= defect in four SQL generators, two stale entries in the
  core-link baseline, and three failing codegen tests. =xml-benchmark-recorded=
  fails because the scratch repository has one commit.
- Build, database and service gates were not run. Their numbers come from CI
  step durations or from ORE Studio's own local_checks reports, as marked.
  =ticks-smoke= has no recorded time. =nightly-linux= and =nightly-windows=
  have no recent successful run, so their times are from failed runs.
- CI step durations have 1 s resolution and steps under 2 s were not listed.
- Python ran with =-I= through a launcher. A gate that relied on the current
  directory or =PYTHONPATH= would have failed, and none did.
