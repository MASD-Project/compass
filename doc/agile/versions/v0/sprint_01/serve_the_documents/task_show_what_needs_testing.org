* Goal

A tester asks what needs testing in an environment and gets the present
sprint's stories, each story's test scenarios and each scenario's state from
its latest run there: untested, failed, passed or changed, with the open note
counts. A developer asks for the same sprint's stories and tasks with their
states. Both are library functions in =compass.db=, as search is, so the HTTP
routes and MCP tools that will be generated from the service's models call
them and add nothing.

* Acceptance

- =compass.db::query::what_needs_testing(connection, view_filter,
  sprint_request)= returns a =testing_response=: the sprint, its stories in
  path order, each with its campaign in the environment when it has one, its
  open note count and its scenarios, and the environment's =synced_at=.
  =sprint_state(connection, view_filter, sprint_request)= returns the
  sprint's stories with their tasks and the State row of each. The types are
  plain structs shaped as search's are; no JSON is read or written, and no
  route or MCP handler is built.
- The sprint is the present one by default: the sprint page whose State is
  =STARTED=, the latest created when several are. An earlier sprint is asked
  for by its =:ID:=, its title or the name of its directory. No such sprint,
  and an unknown environment, are errors.
- A sprint's stories are search's sprint membership, =corpus.sprint_members=,
  of =type = story=; a story's scenarios are the =test.scenario= rows placed
  in the environment whose =story_id= is the story. A story's tasks are the
  =task= pages whose preamble links to it. The caller's view applies to
  sprints, stories, scenarios and tasks.
- A scenario's state comes from its latest finished run in the environment,
  by =finished_at=: none is untested; failed or blocked is failed; passed
  against the scenario's current =definition= is passed; passed against
  another is changed. An unfinished run changes nothing, and neither do runs
  and notes of another environment.
- Each scenario carries the open notes naming it in the environment and each
  story the open notes of its campaign; addressed notes are not counted.
- Each behaviour has a Catch2 test on a throwaway cluster, and two of them
  fail on an injected fault.

* Plan

1. =types/testing.hpp=: the request, the responses and the four states.
2. =query/testing.hpp=: =what_needs_testing= and =sprint_state=, one SQL
   statement each once the sprint is found, with the state derived in C++
   from the latest run.
3. Tests on a small corpus of two sprints, three stories and three
   scenarios in two environments, with activity rows written by SQL, because
   the writes are the next task's.
4. =compass-bench testing=: asks both questions, prints the counts by state
   and times them. =evidence/testing_ore_studio.sh= syncs ORE Studio into a
   private cluster, asks, writes a few activity rows and asks again.

No schema change: the tables of migration 1 and the sprint membership of
migration 2 answer both questions.

* Notes

- *Two STARTED sprints.* ORE Studio has Sprint 28 and Sprint 30 both
  =STARTED=. The design says the present sprint is the one whose state is
  =STARTED=; with two, the latest created is taken, and the response names
  the sprint it chose. A tester who wants the other asks for it by name.
- *Latest run.* The latest finished run, by =finished_at= and then by id. An
  unfinished run is a tester at work and says nothing yet.
- *Changed.* A run records =definition=, the hash of the page without its
  results and State row, so a result written into the page by older tooling
  does not make a pass changed; a test edits the page both ways.
- *Which campaign.* Runs and notes are read by environment and scenario
  =:ID:=, not by campaign, so a scenario moved to another story keeps its
  history in the environment.
