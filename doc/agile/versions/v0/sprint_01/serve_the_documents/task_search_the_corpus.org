* Goal

The document service answers a search with the sections that match, best
first, each with its document's metadata, the anchor of its heading and a
snippet, inside the caller's view and any filter on the documents' metadata,
with counts of each filter's values. The query functions live in
=compass.db=, so the HTTP routes and MCP tools that will be generated from
the service's models call them and add nothing.

* Acceptance

- =compass.db::query::search(connection, view_filter, search_request,
  ranking)= returns a =search_response=: hits, the total of matching
  sections and the environment's =synced_at=. =facets(connection,
  view_filter, facets_request)= returns a =facets_response=. The request and
  response types are plain structs shaped as the investigation's
  =search_request= and =search_response= messages; no JSON is read or
  written, and no route or MCP handler is built.
- The query is =websearch_to_tsquery= under the database's stored text
  search configuration over =corpus.section.tsv=, ranked by =ts_rank_cd=,
  with the document type as a tie-break through the ranking's type order.
- A hit carries the document's =:ID:=, title, type, description and path in
  the environment, the section's heading path and anchor, a =ts_headline=
  snippet and its rank. Hits are paged by limit and offset; the total is
  the same on every page, including a page past the end.
- The filters are type, tags, state, sprint, level, audience, keywords and
  properties, applied to the environment's placements inside the caller's
  view condition. State is the =State= row of the document's =* Status=
  table. Sprint is decided from the documents' links: see Notes.
- Facets count each filter's values over the documents the query matches.
- An unknown environment is an error, never a default.
- A search hit's anchor is the =id= compass.html gives the heading:
  =compass.db= calls =compass.html::ops::heading_anchors= and has no slug of
  its own, and a test renders a document and compares.
- Each behaviour has a Catch2 test against a throwaway cluster: ranking
  order and the type tie-break, each filter, the view, environment
  isolation, facets, paging, snippets and hit fields.
- A recorded set of 25 questions over ORE Studio scores the ranking on
  hit@1, hit@5 and MRR, and can be rerun; the best of the variations tried
  is the default.
- EXPLAIN on ORE Studio's corpus shows every filter and the search using an
  index; latency is reported cold and warm.

* Plan

1. Make the corpus's anchors the renderer's: =ops::extract= calls
   =heading_anchors=, and =db::ops::slug= goes. =compass.html= depends on
   =compass.org= alone, so =compass.db= depending on it makes no cycle in
   the domain layer.
2. Migration 2: a generated =state= column and its index, and a function for
   a sprint's members. Migration 1 is not edited.
3. =types/search.hpp= and =query/search.hpp=: the request and response
   structs, =search= and =facets=, one SQL statement each.
4. Tests on small corpora.
5. =compass-bench search=: reads a question set, runs each question through
   =search=, scores it and times it. The question set and a script that
   syncs ORE Studio into a private cluster and runs it go in =evidence/=.
6. Try two ranking variations, keep the best, check the plans.

* Notes

- *Sprint.* A document is in a sprint when it is the sprint page, when its
  preamble links to the sprint page, or when its preamble links to a story
  whose preamble links to the sprint page. The preamble is the sentence
  each page of the contract opens with to name its parent: a story and a
  test scenario name their sprint there, a task names its story. Links under
  a heading are not followed, because a page links to related stories and
  past sprints in its body. The sprint page and the story must be placed in
  the same environment. =corpus.sprint_members(environment, sprint)= walks
  the links backwards from the sprint through =link_target_id=; the first
  version walked forwards from each document and cost 573 ms over ORE
  Studio's corpus against 15 ms.
- *State.* A generated column over =source=, the first table row named
  =State=, so documents already in a corpus get it when the migration runs
  and the sync writes nothing new.
- *Ranking.* Without normalization, =ts_rank_cd= rewards a long section that
  holds every word: =Product backlog — inbox=, one section of 1.4 MB, was the
  first document for most questions. Normalization 2 divides by length and
  nearly doubles MRR. The weights stay at PostgreSQL's defaults.
- *Recall.* =websearch_to_tsquery= requires every word, so a question
  phrased differently from the page finds nothing: =what is tom next= finds
  8 sections and none is the answering page. Seven questions miss this way.
  An =or= between the words, or a fallback to it when the strict query finds
  little, is the next change to measure.
- *Latency.* A typical search, =nats subject naming=, ranks its 410
  sections in 13 of its 15 ms, reading section pages from disk. The slow
  queries are those with few hits, whose first page holds a huge section:
  =ts_headline= over the 1.4 MB backlog section alone takes 124 ms. Capping
  the text a snippet reads would remove the tail.
- *Indexes.* Every filter and the search use an index already in migration
  1 or the new =document_state=. The environment's placements are read by a
  sequential scan when every placement is in one environment, which is the
  right plan there; =placement_hash= serves the join otherwise.
- *Types.* The structs follow the investigation's operation model: the
  environment is a field of the request, the view is passed beside it, as
  the caller's header will be. They are deleted when the generated messages
  land.
