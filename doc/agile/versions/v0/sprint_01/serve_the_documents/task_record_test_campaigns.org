* Goal

A tester, who has no git, records a test campaign through the service: starts
a run of a scenario, gives each step an outcome and notes, attaches
screenshots, writes notes on the campaign, and finishes the run, whose
outcome the service derives. A developer addresses the notes. Each record
names its tester, and each run the scenario's =:ID:= and the definition it
followed, so the scenario pages stay read-only. The writes are library
functions in =compass.db=, beside what needs testing, which reads them.

* Acceptance

- =compass.db/query/campaign.hpp= has six writes, each in one transaction:
  - =start_run= creates the campaign of the scenario's parent story in the
    environment on the first run, recording its sprint, and records the
    tester, the scenario's =:ID:=, its definition and its document hash. It
    returns the run, the campaign and that definition's steps.
  - =record_step_result= records or replaces a step's outcome (pass, fail,
    blocked or skipped) and notes on an unfinished run.
  - =attach_screenshot= stores a PNG, JPEG, GIF or WebP once, under its blob
    ID, and attaches it to a run, at a step or to the whole run, or to a
    note. Attaching the same bytes to the same place again changes only the
    caption.
  - =add_note= adds an open note to a campaign, of one of the project's note
    kinds, optionally naming a scenario of the campaign's story and one of
    that scenario's steps.
  - =address_note= marks an open note addressed, with the addresser and an
    optional reply.
  - =finish_run= sets the outcome: failed if any step failed, blocked if any
    was blocked and none failed, passed if every step passed or was skipped.
    A run with a step that has no result, and none failed or blocked, is
    refused, naming the steps.
- Every write names its tester; a blank or empty tester is refused and
  nothing is written. A refusal is =rejected_write= with a reason, invalid,
  not found or conflict, for the generated routes to map to a status.
- The request and response types are plain structs, as search's are. No
  JSON is read or written, and no route or MCP handler is built.
- What needs testing reads what these write; a Catch2 test moves a scenario
  through every state with them.
- Each write's validation has a Catch2 test on a throwaway cluster, and two
  of them fail on an injected fault.

* Plan

1. =types/campaign.hpp=: the requests, the responses, the step and run
   outcomes and =note_kinds=.
2. =ops/run_outcome.hpp=: the outcome rule as a pure function, tested
   without a database.
3. =query/campaign.hpp=: the six writes. Each locks the run or note it
   writes to (=FOR UPDATE=), so a finish cannot race a step result, and an
   attachment's place is looked up under that lock.
4. =compass-bench campaign= plays a script of writes, one a line, and
   reports each result or refusal. =evidence/campaign_ore_studio.sh= plays
   one on ORE Studio's present sprint.

No schema change. The tables of migration 1 hold every record; the design's
key of =attached= (attachment, run or note, step) is kept by the write, under
the lock of the run or note, rather than by a unique index, which would need
=NULLS NOT DISTINCT= that the entity model's index table cannot state. The
entity models of =projects/compass.db/modeling/= are unchanged, so their
comparison with the SQL is unchanged.

* Notes

- *The tester moves from the body to the caller* (2026-11-23).
  [[id:AF30B206-2FAB-435F-819F-9EC652D4E40D][Design: aligning the document service with ORE Studio's HTTP and MCP]]
  takes the tester from the gateway's subject header, records the subject and
  the acting agent of every write in a new =activity.action= table, and
  removes =tester= from the six requests. The change is carried by
  [[id:186C4AF8-CAB4-4754-B8AC-76D571B1B3E9][Serve the documents over HTTP]],
  where the caller first exists; this task's writes stay as merged until then.
- *Note kinds come from the compass configuration.* The design puts them in
  =.compass.org=, beside the views, and so does this task. A check document
  under =compass/checks/= defines a rule that =compass check= runs over a
  checkout's files; note kinds are no rule over files but the vocabulary of
  the service's own records, read by the service, as the views are. The
  service already needs =.compass.org= for its views, and
  =read_repository_file= reads it from a commit, as a release deploy will,
  with no checkout. So the writes take =note_kinds= as an argument, as
  queries take the =view_filter=: the service parses the configuration once,
  at its boundary, and the library trusts what it is given. The parse of a
  =* Note kinds= table, one kind a row, comes with Serve the documents over
  HTTP, which wires the views from the same file.
- *Runs follow one definition.* =start_run= returns the steps of the
  definition the environment holds at that moment, and every later write to
  the run checks steps against the run's own document, not the current one,
  so an edit to the page during a run never mixes step lists.
- *A scenario with no parent story* cannot be run: a campaign is a story's.
  Whether a regression suite outside any sprint may be run is still an open
  question of the design.
- *Unfinished runs* are left as they are. A retried =start_run= makes a
  second run; neither counts until it finishes.
