* Goal

An environment that needs the code of a release can run it before the
release's packages are attached. Every merge to =main= builds the Linux
packages, and =install_compass.sh --build <commit|main>= installs them with
the usual layout. =--version= marks such a build as a pre-release. The
official release is unchanged: the signed tag rebuilds compass and its runs
attach the packages.

* Acceptance

- Continuous Linux runs on every push to =main= and uploads the
  =linux-clang-release-ninja= artifact, holding the =.deb= and the
  =.tar.gz=, for 30 days.
- =install_compass.sh --build main= installs the newest green build of
  =main= that holds the artifact. =--build <commit>= installs the build of
  that commit and refuses a package of any other commit.
- =--version= of such an install reads
  =tag: none (pre-release build from <run URL>)=.
- =--build <commit>= installs the release instead when that commit's release
  carries its Linux archive.
- The recipe How do I unblock environments before a release finishes? says
  how to use it.

* Plan

- Add =push: branches: [main]= to =continuous-linux.yml=. A push builds
  release only, as a pull request does, and the relevance guard compares it
  with the commit before the push, so a merge that changes only documents
  builds nothing.
- Run cpack on the release build of =main= as well as of a tag, and upload
  the packages of both.
- In =install_compass.sh=, find the run through the GitHub API with =gh=,
  download the artifact with =gh run download= and unpack it the way a
  release is unpacked. Then write =prerelease=<run URL>= into the installed
  manifest.
- In =compass --version=, append the run to the =tag: none= line when the
  manifest names one. The line keeps its first word, so a reader that parses
  =tag:= still sees =none=.

A first design promoted main's build as the release: it removed the tag
rebuild and moved the version into a =VERSION= file. The product owner kept
the official release as it is, so that design was dropped.

* Notes

- A main build of the commit being tagged is ready about as soon as the
  tag's own Linux packages: both are one release build of about 12 minutes.
  The time saved is the wait between merge and tag, and the wait for a
  release when a commit merged earlier is needed now. The macOS and Windows
  packages still come only from the tag.
- GitHub serves workflow artifacts only to an authenticated client, so
  =--build= needs =gh=. The release path still needs only =curl=.
- ORE Studio's bearings check, =compass_ng_problem= in
  =projects/ores.compass/src/compass.py=, compares only commit times. Run
  against the =--version= of a pre-release build of the pinned commit, with a
  pin that names =release: v0.0.13=, it reports no problem. The check
  therefore stays satisfied after the release is out. ORE Studio needs to
  read =release:= from the pin as well. When the pin names a release and
  =--version= reports =tag: none (pre-release=, the check should report that
  the build is a pre-release. With that change the same output is reported,
  and an install of release v0.0.13 is not.
