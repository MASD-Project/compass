* Acceptance

- The include graph for all ORE Studio C++ is built and timed; unresolved includes are counted.

* Plan

- Add an =includes= stage to =compass-bench=. It scans every C and C++ file in
  the file table (=.hpp=, =.cpp=, =.h=, =.hh=, =.cc=, =.cxx=, =.ipp=, =.tpp=)
  for =#include= lines with a hand-written scanner over the mapped bytes: no
  regex, no preprocessor, skipping comments and string literals.
- Resolution reads =compile_commands.json= once: the =-I=, =-iquote= and
  =-isystem= directories per translation unit, rebased from the build's source
  root onto the checkout being measured. Quoted includes try the includer's
  directory first. A target inside the checkout is an edge; a target found
  outside it (vcpkg, the system) is external; anything else is unresolved.
- Data shape: an include table in struct-of-arrays form (includer file id,
  target file id or external or unresolved, line), and the graph as compressed
  sparse rows over file ids, built once after scanning.
- Report: scan time and resolve time separately, includes found, edges,
  external, unresolved (with the top unresolved names), and the top headers by
  direct fan-in. Transitive fan-in is computed and timed too, so its cost is
  known before Analyse C++ and SQL depends on it.
- The measurement uses an archive of the ORE Studio commit that the
  =compile_commands.json= was generated from, so paths agree.

* Result

- =compass-bench includes= scans every C and C++ file with a hand-written
  scanner, resolves each include through =compile_commands.json= rebased onto
  the checkout, builds the include graph as CSR and computes transitive fan-in.
- The whole ORE Studio include graph costs about a quarter of a second: 132 ms
  to scan on 8 threads, 120 ms to resolve on one, and under 3 ms for the graph
  and every header's transitive fan-in. Resolving is single-threaded and is the
  obvious next speed-up.
- 52 of 206,485 includes stay unresolved, each with a known cause: Windows-only
  headers under =#ifdef=, files no compile command builds (prototypes, scripts,
  vendored ORE tools), one cross-component test fixture, and one stale
  generated include.
- ORE Studio builds in unity mode, so its compile commands name generated
  =unity_N_cxx.cxx= files; =--source-root= is required, and each command is
  anchored at the build directory above =CMakeFiles=.
- A header takes its component's include directories. The compiler uses the
  directories of whichever translation unit includes it, so a header shared
  across components can resolve differently; this caused one of the 52.
- Review found that a relative =--source-root= resolved nothing inside the
  checkout while still exiting 0. Paths are now made absolute at the CLI
  boundary, and every path form gives the same counts.
- 15 defects injected into the scanner and resolver were all caught.
