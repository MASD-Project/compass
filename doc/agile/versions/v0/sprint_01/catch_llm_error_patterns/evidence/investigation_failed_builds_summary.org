A point-in-time record, written while the story that commissioned it was open, of an [[id:A7F8D9E2-3C4B-4A5D-B67C-8E9F0A1B2C3D][investigation]] into the patterns behind ORE Studio's failed CI runs and which of them compass could catch before a build. It is evidence for the [[id:694CC015-2319-4A60-A912-C47D01BA70E1][Mine failed builds]] task and was written on 2026-11-18.

It is a snapshot, not a description of the system. The run-by-run record
is [[id:080067B0-D941-4D41-9388-24E39AD37E9C][Investigation: ORE Studio failed builds by day]].

* Context

The [[id:63D5482E-E1E7-45B0-883F-3B2DDFA2B447][Catch the errors LLMs introduce]] story wants checks that stop the
errors LLMs introduce into ORE Studio before a build. To choose them it
needs to know why ORE Studio's CI failed over the last two months, how
often and at what cost, and which failures a compass check could have
caught. Most of ORE Studio's commits in the window carry a model's
co-author trailer, so most failures are LLM-authored changes; the question
this page answers is which of them a check before the build would stop.

* Methodology

The data came from GitHub through the =gh= CLI and was classified offline.

#+begin_src sh
python3 -I build/scripts/mine_failed_builds.py --cache "$CACHE" fetch \
    --since 2026-09-19 --until 2026-11-18 --delay 1.0 --workers 6
python3 -I build/scripts/mine_failed_builds.py --cache "$CACHE" report \
    --clone ~/Development/OreStudio/ores.git
#+end_src

- =fetch= ran on 2026-11-18 from 14:43 to 16:26 UTC against
  =OreStudio/OreStudio=, restarted along the way as the task's Notes
  record; the last run made 3,523 requests and waited 21 minutes once for
  the rate-limit reset. It lists, one UTC day at a time, every run whose
  conclusion is =failure= or =startup_failure=, then fetches the jobs of
  each run's latest attempt and the log of each failed job. A cancelled
  run is not listed; a job cancelled because a sibling failed is listed
  only when no job of its run failed.
- The cache was =$CACHE= in the session scratchpad on tmpfs. Logs are
  trimmed to the failing step's tail and the error lines, then gzipped,
  so the cache stayed small; Counts gives its size. It is not committed.
  A rerun of =fetch= over the same range fetches only today's and
  yesterday's listings and any run it has not seen.
- =report= reads only the cache and the local clone of ORE Studio. It
  rewrites the generated blocks of this page and of
  [[id:080067B0-D941-4D41-9388-24E39AD37E9C][Investigation: ORE Studio failed builds by day]].
- A failure is one failed job, or one run that failed with no failed job.
  Its step is the first step of the job that failed, its reason the first
  real error of that step, normalised. The pattern is the first entry of
  the script's =PATTERNS= table whose workflow, step and error expressions
  all match.
- Minutes are failed-job minutes: the wall time of the failed jobs. They
  leave out the passing and cancelled jobs of the same runs, so they
  understate what a failure cost. Heads count distinct head commits, and
  Days the days the pattern appeared on.

Each verdict means one thing.

- already caught :: a compass codec catches it today; the Codec column
  names it. Those failures reached CI because compass did not run before
  the push, not because a check is missing.
- could be caught :: a compass check could catch it before a build, from
  data compass loads or could load; the column names that data.
- not catchable :: only a compiler, a test run or the runner shows it;
  the column gives the reason.
- (guess) :: the verdict was inferred from the error message alone,
  without reading the tree at that commit.

* Paths taken

- A single query over the window reported 2,500 runs whether or not it
  filtered on failure, a capped figure, and a filtered listing returns at
  most 1,000 runs. The script lists one day at a time instead and found
  2,888 failed runs; no day came near the cap.
- The first log trimming kept the tail before the last =##[error]=. That
  annotation is usually written by a clean-up step that runs after the
  failure (a cache save, =sccache --show-stats=), so the tail missed the
  failing step. The tail now ends at the first =##[error]=.
- The first error was first taken as the first line matching "error".
  That picked up file names in the site build's publishing log
  (=trade-import-failed-state.org=), test names, application log lines and
  CTest's post-failure messages. Tiers, path stripping and a list of
  pointer lines replaced it; the task's Notes give the order.
- A commit was first called LLM-authored only on a Claude trailer. ORE
  Studio's commits also carry DeepSeek trailers, so any model named in a
  =Co-Authored-By:= trailer now counts. A merge is judged by the commits it
  brought in.

* Conclusions

** Findings

ORE Studio's CI failed 2,889 times in the 61 days from 2026-09-19 to
2026-11-18. Those runs held 13,973 jobs, 4,774 of which failed, for 4,841
classified failures once the runs that failed with no failed job are
added. Every failure but 63 matched one of 94 patterns; the 63 are 31
jobs whose log GitHub no longer served and 32 listed under Unclassified.

- *Most failed runs were already catchable.* Patterns compass catches
  today account for 1,925 runs, two runs in three. Nearly all of them are
  ORE Studio's own gates: generated output drifting from its model (810
  runs), the shell recipe inventory (442), the ER diagram (347) and
  unseeded handler permissions (197, and 196 more through the codegen
  suite). These fail fast and cheaply, 11,935 failed-job minutes in all,
  but each is a round trip: the gate existed, and nobody ran it before
  pushing. A run counts under every verdict its jobs fail with, so the
  verdict rows add up to more than 2,889.
- *The catchable patterns compass lacks cost more per run.* The 24
  could-be-caught patterns account for 650 runs and 31,349 minutes. By
  count they are led by TypeScript formatting (229 runs), a generated
  domain header's includes (93), site links (52), MSVC's reflection depth
  limit (50, a guess), standard-library facilities a platform lacks (34, a
  guess) and pasted blocks that name a missing symbol (33). By cost they
  are led by the portability failures that only Windows and macOS builds
  show: the standard-library facilities (9,533 minutes), includes that do
  not resolve (7,756; 24 of their 47 jobs are =unistd.h= on Windows) and
  the reflection limit (6,076). A failed job of these three patterns
  ran for 70 to 165 minutes on average before it failed.
- *What compass cannot catch costs the most.* 540 runs and 113,878
  minutes went to test failures (39,084 minutes), step time-outs (17,344),
  compilers out of memory (13,636), compile errors (9,510), full disks
  (8,249) and a lost or stopped runner. Nothing in the tree predicts most
  of them; the time-outs and memory failures may follow the tree's
  growth, which this page did not test.
- *The codegen suite is mostly tree checks.* Of the 491 failures of =Run
  the codegen suite=, 448 come from test files that check the tree, not
  the generator: =test_handler_permissions= (196),
  =test_domain_includes= (93) and others; 43 come from tests of the
  generator itself. Eleven of the tree-checking files that failed have a
  compass codec. Four do not, =test_domain_includes=,
  =test_provision_step_words=, =test_sql_name_base= and
  =test_entity_typescript=, and they appear among the candidates below.
  A suite failure is classified by the first entry of =PATTERNS= whose
  test failed, so a run that broke two such files counts once.
- *The LLM trailer does not single out the failing commits.* 1,503 of
  the 1,754 distinct head commits of failed runs (86%) carry a model's
  co-author trailer or merge commits that do. Across all 14,839
  non-merge commits in ORE Studio's clone over the window the share is
  79%. On this evidence the failures track the volume of LLM-written
  change rather than a higher error rate per change; the trailer cannot
  tell the two apart.

** Catchable patterns

The could-be-caught patterns come first, by runs, then the already-caught
ones. The example run is the pattern's earliest pull-request run, or its
earliest run when it never failed a pull request; the event is given when
it is not a pull request. A push or schedule run's head is main's tip,
usually a merge, so the commit that introduced the error is among those
the merge brought in rather than the merge itself. LLM heads counts the
distinct head commits that carry a model's co-author trailer, or merge
commits that do, out of the heads the local clone holds.
