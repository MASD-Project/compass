* Goal

=compass check --ratchet= fails only on what the change made worse. A
generated file whose header names a script the tree lacks
(=names_missing_file=) was reported only for the checkout, never for the
merge base, so every such finding was new on every ratchet run. On a copy of
ORE Studio's main with one trivial commit on top, the ratchet failed with four
new =tangle/names_missing_file= findings that the change did not cause.

* Acceptance

- A ratchet excuses a missing script that the merge base already named.
- A ratchet reports as new a missing script that the change names for the
  first time.
- A ratchet reports as new a script that the change deletes while a
  generated header still names it.
- On a copy of ORE Studio's main with one trivial commit, the ratchet reports
  no new =names_missing_file= findings.

* Plan

=names_missing_of= read an =output_plan=, the plan for writing outputs to
disk, which exists only for a checkout. The check of a commit builds the
outputs but no plan, so it never called =names_missing_of=. The rule itself
reads nothing from disk: it scans the bytes the codec generates and the file
listing, and for a commit that listing comes from the commit's tree.

- =names_missing_of= reads the =output_set=, which a checkout and a commit
  both have, instead of the plan. A removed output has no row in the set, as
  it had no contents in the plan.
- The check of a commit adds the findings after =commit_drift_of=, from
  =p.listed.files=, the commit's tree.
- The checkout and the edit hook keep reporting them only when the plan has
  no problems, as before.

The two branches of =check_in= were compared for other findings that only
a checkout reports:

- =drift= with the =remove= action ("compass wrote this file and X no longer
  generates it") comes from the local written-outputs record, which no
  commit holds. It is left as it is: a fresh clone, which is what CI checks,
  has no record and never reports it, and computing it at the base would
  mean inventing a record.
- Every other drift finding is keyed by the blob IDs of the file and of what
  is generated, and =commit_drift_of= gives the same IDs, so it matches.
- Formatting findings, codec findings and exceptions read through the same
  checkout or commit file source, so both sides report them. Provenance
  findings are added to the new set on purpose.
