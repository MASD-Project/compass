A point-in-time record of an [[id:A7F8D9E2-3C4B-4A5D-B67C-8E9F0A1B2C3D][investigation]] into the data compass-ng reads
out of ORE Studio's Python files. It is evidence for the
[[id:DAB2F48A-E47A-4895-9026-056AF21E6CCC][Let projects define their own checks]] story and the input to the
design and migration plan that moves this data into literate org
documents. It was written on 2026-11-21, at compass =80a2a31= and ORE
Studio =732fc2ee34= (origin/main, exported without =external/=).

It is a snapshot, not a description of the system. The design that acts
on it is [[id:225B524C-1638-4A03-B02F-66EB6759619D][Design: literate project checks]].

* Context

Several codecs ported ORE Studio's Python gates and generators but left
the curated data in the Python. They open ORE's =.py= files as text and
parse module-level assignments out of them with
=ops::python_assignment=, =ops::python_string_constants=,
=ops::resolved= (=compass.crosscheck/src/ops/python_literals.cpp=) and
=ops::module_table= (=compass.crosscheck/src/ops/json_value.cpp:383-392=,
which is =python_assignment=, then =resolved= against the module's string
constants, then =json_of=). One codec, =skill_type_tables=, reads
ORE's =compass.py= with regular expressions instead. The consequences:

- ORE cannot delete a script compass reads, even once compass answers
  for its gate.
- A Python refactor that keeps behaviour (a computed value, a renamed
  constant, a helper call in a literal) breaks a codec.
- Nothing on ORE's side says compass reads the file.

The product owner decided the data moves into compass check documents:
org files that hold each table under a level-1 heading, with prose that
explains it, as =compass/checks/wide_types.org='s =* Ceilings= does.

* Methodology

- The readers. =grep= over =projects/*/src= and =projects/*/include=
  (excluding =projects/compass.legacy=) for =.py=, =python_assignment=,
  =python_string_constants=, =module_table= and =python_dict=. Eleven
  source files name a =.py= path that they read; every other hit is a
  comment, a generated banner or a fix message. The eleven are the files
  the brief named, so there is no other codec that reads a =.py= file as
  data.
- The shapes and sizes. A script parsed each ORE file with Python's
  =ast= module (no import, no execution) and printed, per name, its line
  range, its shape and its entry count. Nested counts (=KINDS= mappings,
  =COMPOSITE_KINDS= parts, =RULES= match shapes, cells holding a =|=)
  were counted by the same means. No size below is estimated.
- The parse sites. Each =file:line= was read in the codec source at
  =80a2a31=.
- The callers. =grep= over the export for imports of each module
  (=import=, =from=, =spec_from_file_location=), for each script's path
  in =build/scripts/local_checks.py=, in =.github/workflows/*.yml= and in
  shell scripts.
- The classes.
  - /curated/: a table a person edits.
  - /machinery/: a regular expression or a function the codec
    reimplements; it belongs in compass code.
  - /template/: output text the codec copies verbatim (a licence block,
    a page header).
  - /provenance/: a name or version string only.

* Conclusions

1. *Much of this is not check data, and some of it is ORE's runtime
   data.* ORE's own tools read the same values while they run:
   =compass.py='s =_STATIC_PARENT= and =_DEFAULTABLE_PARENT= decide
   where ORE's =compass add= writes a document; =ore_files.py='s =FILES=
   is the source of the =reporting_ore_files_populate.sql= seed;
   =COMPONENTS_UNDER_TEST= drives =check_component_drift.py --all=, which
   regenerates code; =COMPONENT_PREFIXES= drives ORE's SQL validator
   (=validate_schemas.sh=). Moving these into a compass check document
   either makes ORE's Python read org or leaves two copies.
2. *Eight of the seventeen files compass reads still run in ORE whatever
   compass does.* =local_checks.py= runs a ported gate
   as Python only when =compass-ng= is not on the PATH
   (=COMPASS_CODECS=, =local_checks.py:1443-1519=). But the codegen and
   build-script test suites, the conventions generator tests, the
   file-types seed and three workflows on push to =main= (=doc-lint.yml=,
   =codegen-drift.yml=, =continuous-linux.yml=) import or run
   =generate_sql.py=, the three route modules, =component_registry.py=,
   =plantuml_er_parse_sql.py=, =ore_files.py=, =compass.py= and
   =generate_skill_type_tables.py= directly. The migration has to retire
   those callers in ORE, or teach them to read the org tables, before
   the data can leave the Python.
3. *Six of the eleven codecs are generators, not checks.*
   =ore_value_sets=, =conventions_dataset=, =route_inventory=,
   =er_diagram=, =ore_output_catalogue= and =skill_type_tables= write
   files (=corpus_function<ct::file_output>=). Their data is a
   generator's input, not a check's parameter, and the =check= document
   type, whose compiler reads only =* Definition=, =* Ceilings=,
   =* Exceptions= and =* Examples= (=check_documents.cpp:166-185=,
   =395=), has no place for it. A data-table document type, or a
   generic table reader, is needed whatever the home.
4. *Three tables strain an org table.*
   - =route_classification.RULES=: 289 ordered rows whose first match
     wins; 133 are regular expressions and 113 of those hold a =|=. An org
     table needs =\vert= for each, and compass's org reader does not
     unescape it (=compass.cli/src/config/org_reader.cpp:30-35= strips
     only === and =~=).
   - =generate_sql.KINDS= and =COMPOSITE_KINDS=: nested three deep
     (kind, part, column mapping), with two parts lists computed by
     Python functions. They flatten into five tables, and the two
     functions stay code. The design's rule ("a check that needs nesting
     is a sign it should be code") applies to the functions, not to the
     mappings.
   - Two =HEADER= values are multi-line output templates (42 and 58
     lines). They belong in a source block or a template file, not a
     table.

A fifth point affects scope rather than shape: the same data is stated
more than once. =CATALOGUES= and =SCHEMA_TYPE_SETS= are identical in
=convention_value_sets.py= and =curve_value_sets.py=; =INDEX_FIELDS= is
identical in =propose.py= and =generate_sql.py=; =PERIOD_PATTERN= repeats
=OWN_SETS["convention.period"]["pattern"]=. compass also holds copies it
does not read (see [[*Data compass copies instead of reading][Data compass copies instead of reading]]).

* Risks and open questions

- Two writers of one output. Where ORE still runs a generator in CI
  (=generate_skill_type_tables.py --check=, =plantuml_er_generate.py=,
  =check_component_drift.py=), the Python's copy of the data and the
  org table must stay equal, or one of the two fails. Each such script
  must be retired, or read the org table, in the same change that moves
  the data.
- Runtime data. =_STATIC_PARENT=, =_DEFAULTABLE_PARENT=, the subparser
  help, =FILES=, =SCHEMAS=, =COMPONENTS_UNDER_TEST= and
  =COMPONENT_PREFIXES= serve ORE's own tools. Their home is ORE's
  decision; compass should read them where ORE keeps them, not own a
  copy.
- Where the documents live. The design puts check documents in ORE's
  =compass/checks/=. Much of this data is a generator's input
  (value sets, conventions, routes, output catalogue). Is a generator's
  data a check document, a new document type, or a dataset under the
  component that owns it?
- The table reader. The check compiler reads named tables only
  (=* Ceilings=, =* Exceptions=). Every codec here needs a generic
  reader of a named table with named columns, and a rule for empty
  cells: =None= values (=ITEM_WORDS["text"]=, =LIST_ITEM= sources,
  =KINDS= decoded fields, =TYPE_OVERRIDE='s any-element key) and the
  empty string (=NULLS=, =TABLE_STYLES= stereotypes) are both
  meaningful today.
- =\vert=. 113 route rules hold a =|= in a regular expression. Either
  compass's org reader unescapes =\vert= in cells, or the patterns
  leave the table.
- Order. =RULES= is first-match; =PREFIXES=, =KEYS= and
  =COMPONENT_PREFIXES= (where =ores_dq_= and =ores_dq_fsm_= overlap) may
  be order-sensitive. The reader must keep row order.
- Size. =route_classification.py= is 1,879 lines, most of it notes; as
  one org table its rows run to 643 characters. A table per area may
  read better than one table.
- Duplicates to decide once: =CATALOGUES= and =SCHEMA_TYPE_SETS= (two
  value-set modules), =INDEX_FIELDS= (=propose.py=, =generate_sql.py=),
  =PERIOD_PATTERN= and the =convention.period= pattern, the =BDC= maps in
  opposite directions (=propose.py=, =generate_sql.py=), and
  =COMPONENTS_UNDER_TEST= (two codecs).
- Schemas of JSON files. =CURATION_KEYS= and =SOURCES= validate
  =curve_value_set_curation.json=; moving them without the JSON splits
  one contract across two formats.
- The brief's premise about =extract.py=: =conventions_coverage= does
  not read the TSV =extract.py= writes; it reimplements =extract.py= and
  reads =decisions.tsv= and =builtin_index_fields.tsv= directly.

* Recommendations

The product owner decided on 2026-11-21, from this inventory:

- Move the curated data into check documents, org tables with prose,
  which the codecs read through their data option, as the =* Codec data=
  section of [[id:225B524C-1638-4A03-B02F-66EB6759619D][Design: literate project checks]] describes.
- Phase it. First the infrastructure and the nine files only compass reads
  (=conventions_coverage=, the value sets, the output catalogue); that
  gates v0.0.5. Then the eight files ORE Studio's own tools still run, each
  in the change that makes those tools read the org table, so there is one
  copy.
- Data a tool of ORE Studio's also needs lives in the check document, and
  the tool reads the table.
