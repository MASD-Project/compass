* Goal

The operation model type exists, but it says how to reach a
message over NATS, not over HTTP or MCP. Add =:http_method:=, =:http_path:=,
=:http_in:=, =:tool:=, =:area:=, =:entity:=, =:writes:= and =:caller:=, named
after ORE Studio's route catalogue declaration as
[[id:AF30B206-2FAB-435F-819F-9EC652D4E40D][Design: aligning the document service with ORE Studio's HTTP and MCP]] decides (=:caller:= is =view= for a read and =subject= for a
write), and
write the operation models of Serve the documents' endpoints and tools, as
[[id:7FD52505-1436-4925-A1DE-4A3EC88F0133][Investigation: How compass generates itself]] sketches for search.

* Plan

The models come first, ahead of the move, as for
[[id:02089780-F445-4220-89E1-3CBCA0347B37][Model compass's tables]], so the
product owner can review the form before any loader, context or template is
written.

- A new component folder, =projects/compass.serve/=, with only =modeling/=:
  its component overview and four operation models: the document reads, the
  sprint and campaign reads, the campaign writes and the refusal. The design
  names =compass.serve= as the service's home, and the routes must not live
  in =compass.db=, which would then depend on the HTTP server's libraries.
  The folder is not a CMake target until the service task adds code.
- =#+type: masd.codegen.operation=, beside the entity models'
  =masd.codegen.entity=.
- Each message whose struct exists in =compass.db/types= repeats it member
  for member: name, =:cpp_type:=, and =:default:= as the C++ initialiser.
  [[file:evidence/service_model_struct_check.py][evidence/service_model_struct_check.py]]
  compares them, with the new messages, the unmodelled structs and the
  changes the alignment design makes to the six write requests pinned.
- Messages for the endpoints with no C++ yet (the document list, one
  document, backlinks, environments, version, sync, a run and a campaign's
  notes) are new, named as the investigation's table names them.
- The new properties are =:http_method:=, =:http_path:=, =:tool:=,
  =:area:=, =:entity:=, =:writes:=, =:destructive:=, =:idempotent:=,
  =:summary:=, =:caller:= and =:max_body_size:= on a request, and
  =:http_in:=, =:http_name:=, =:required:=, =:encoding:= and =:values:= on a
  field. The component overview of =compass.serve= defines each one, and how
  a route and a tool bind a request and refuse one; it is the draft of the
  feature pages.
  [[file:evidence/service_model_binding_check.py][evidence/service_model_binding_check.py]]
  holds the models to it.
- The catalogue properties take ORE Studio's vocabulary, by the product
  owner's requirement that compass's HTTP and MCP align with ORE Studio's:
  each is a member of =route_catalogue= in ORE Studio's
  =ores.http.api/domain/route.hpp=, whose gate refuses a route without a
  tool, an area and an entity. The investigation's =:mcp_tool:=,
  =:mcp_title:= and =:read_only:= became =:tool:=, =:summary:= and
  =:writes:=. Every request has a tool, so sync also has a route. A read's
  tool starts with one of the prefixes by which ORE Studio's catalogue knows
  a read. The areas are compass's own three, =documents=, =agile= and =qa=,
  and the entities are =document=, =environment=, =service=, =sprint=,
  =scenario=, =run=, =attachment= and =note=.
- The caller is never a field. A read needs a view and a write a view and a
  subject, from the gateway's three headers, as the alignment design
  decides. The six write requests lose =tester=; the structs follow in
  [[id:186C4AF8-CAB4-4754-B8AC-76D571B1B3E9][Serve the documents over HTTP]].

* Notes

** What loads

In compass's own checkout the codegen codec is off, as the entity models
found, so =compass-ng check= reads these models only as documents and
nothing is written into compass's tree.
[[file:evidence/service_model_load_probe.sh][evidence/service_model_load_probe.sh]]
loads each model on a scratch copy of ORE Studio, in three stages. Every
=exit= in its output is =compass-ng diff='s: 0 when nothing would change, 1
when it finds a change, so 1 is the expected result of a stage that writes
files, and 2 would be a failure.

| Stage | Change to the models | Result for all 4 |
|-------+----------------------+------------------|
| =as_written= | None. | Skipped: =masd.codegen.operation= is not a codegen type. No output, and stderr holds only the run's summary. |
| =ores_type= | =#+type: ores.codegen.operation=. | Loads, and stderr names no error or warning. Writes the C++ protocol header and its TypeScript twin. The struct check finds the header's structs to be the model's messages, member for member, in =namespace compass::db::types=. |
| =facets_on= | Also ORE Studio's protocol, wire codec and HTTP route facets on, and =:http_route: true= on each routed request. | Loads. Adds the JSON wire codec, its round-trip tests, a route file and a Hurl recipe page. The route file registers 0 endpoints and the recipe page lists none, because ORE Studio's route needs a NATS =:subject:=. No =/v1/= path and no MCP text reaches any output. |

The probe compiles nothing. That the outputs would not compile is inferred:
the struct check notes that each header uses =step_outcome=, =run_outcome=
or =scenario_state= and declares none of them.

** What compass's loader does not understand yet

The loader reads a message's =:subject:=, =:response:=, =:auth:=,
=:destructive:=, =:http_route:=, =:rate_policy:=, =:shell_command:=,
=:request_timeout_seconds:= and =:shell_adopts_token_for:=, and a field's
=:cpp_type:= and =:default:= (=projects/compass.model/src/ops/messages.cpp=,
=declared_messages=). It drops every other property without a word. This
list is the input to [[id:E754BE53-3A6B-4491-BB26-450D1A34F159][Generate JSON codecs]]
and [[id:8CF40A62-82EB-4FE0-8CEC-2621BD0E66FE][Generate the HTTP and MCP service]].

| What | Where | What happens today |
|------+-------+--------------------|
| =#+type: masd.codegen.operation= | header | Not in the codec's list of codegen types; the page is skipped. |
| =:http_method:=, =:http_path:= | request | Dropped. A route is only made from a =:subject:=, as =POST /api/v1/<subject>=; without one the route file registers nothing. |
| =:tool:=, =:area:=, =:entity:=, =:writes:=, =:summary:= | request | Dropped. Nothing generates a catalogue place or an MCP tool. |
| =:idempotent:=, =:max_body_size:= | request | Dropped. =:destructive:= is read as a flag, for ORE Studio's shell, and a value other than true stops the model loading; the first probe run of this review found that, so both hints are flags. |
| =:caller:= | request | Dropped. The only access property is =:auth:=, a session. |
| =:http_in:=, =:http_name:=, =:required:= | field | Dropped. The overview's binding rules have no template yet. |
| =:encoding:= | field | Dropped. The wire codec writes a =std::string= as a JSON string, not as base64. |
| =:values:= | field | Dropped. =scenario_state=, =step_outcome= and =run_outcome= are used and never declared, in C++ and in TypeScript. |
| Prose under a message or a field | body | Not read. The loader reads only a =#+begin_src ... :name comment= block, a Doxygen comment, so the MCP descriptions have no source. |
| No =#+subcomponent:= | header | The route includes =ores.serve./messaging/...=, an empty part, where a simple component has none. |

** Departures from the design and the investigation

- Catalogue vocabulary. The product owner required compass's HTTP and MCP to
  align with ORE Studio's, so the investigation's =:mcp_tool:=,
  =:mcp_title:= and =:read_only:= are ORE Studio's =:tool:=, =:summary:= and
  =:writes:=, with =:area:= and =:entity:= added. Every request has a tool,
  as every route has in ORE Studio, and =/mcp= lists every tool.
- Tool names. The design's =search=, =facets=, =backlinks=, =version=,
  =sync=, =sprint_state= and =what_needs_testing= are =search_documents=,
  =list_facets=, =list_backlinks=, =get_version=, =sync_environment=,
  =get_sprint_state= and =list_scenarios_to_test=. The alignment design
  first named the facet tool =count_facets=; it is =list_facets=, there and
  here, because ORE Studio's catalogue knows a read by its prefix and
  =count_= is not one.
- Search filters. The design's Search section names the metadata filters
  =kw.<keyword>= and =prop.<property>=. The model has one repeated parameter
  each, =keyword=name:value= and =property=NAME:value=, because ORE Studio's
  =query_param= declares one fixed name and cannot declare a family of
  names.
- Sync has a route, =POST /v1/{environment}/sync=, where the design made it
  an MCP tool only, because a tool is a route's catalogue name.
- =finish_run_request= has a route the design's table does not list.
- The design has no route that reads a run or a campaign's notes, so a tester
  could not resume a run and a developer could not find a note's id. The
  model adds =get_run= and =list_notes=.
- The six write requests lose =tester=, and the five that name a row gain
  =environment=, so every route starts at =/v1/{environment}= and a gateway
  can scope every call by the environment in its path.
- C++'s one =sprint_request= is two messages, because a message states one
  route. =add_note_response= wraps the bare id =query::add_note= answers.
- The messages state =#+namespace: compass::db::types=, where the query
  functions take them today, while the models sit in =compass.serve=. The
  codegen writes a model's outputs under its own component: before the
  messages are generated, either the queries move to =compass.serve=, as the
  design placed them, or the protocol facet writes into =compass.db=. This
  is open, and must be decided before [[id:E754BE53-3A6B-4491-BB26-450D1A34F159][Generate JSON codecs]].
