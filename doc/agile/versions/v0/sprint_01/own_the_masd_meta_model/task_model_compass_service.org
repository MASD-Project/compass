* Goal

The operation model type exists, but it says how to reach a
message over NATS, not over HTTP or MCP. Add =:http_method:=, =:http_path:=,
=:http_in:=, =:mcp_tool:=, =:mcp_title:=, =:read_only:= and =:caller:=, and
write the operation models of Serve the documents' endpoints and tools, as
[[id:7FD52505-1436-4925-A1DE-4A3EC88F0133][Investigation: How compass generates itself]] sketches for search.

* Plan

The models come first, ahead of the move, as for
[[id:02089780-F445-4220-89E1-3CBCA0347B37][Model compass's tables]], so the
product owner can review the form before any loader, context or template is
written.

- A new component folder, =projects/compass.serve/=, with only =modeling/=:
  its component overview and three operation models, one per group. The
  design names =compass.serve= as the service's home, and the routes must
  not live in =compass.db=, which would then depend on the HTTP server's
  libraries. The folder is not a CMake target until the service task adds
  code.
- =#+type: masd.codegen.operation=, beside the entity models'
  =masd.codegen.entity=.
- Each message whose struct exists in =compass.db/types= repeats it member
  for member: name, =:cpp_type:=, and =:default:= as the C++ initialiser.
  [[file:evidence/service_model_struct_check.py][evidence/service_model_struct_check.py]]
  compares them.
- Messages for the endpoints with no C++ yet (the document list, one
  document, backlinks, environments, version, sync) are new, named as the
  investigation's table names them.
- The new properties are =:http_method:=, =:http_path:=, =:tool:=,
  =:area:=, =:entity:=, =:writes:=, =:summary:= and =:caller:= on a request,
  and =:http_in:=, =:http_name:= and =:values:= on a field. The component
  overview of =compass.serve= defines each one; it is the draft of the
  feature pages.
- The catalogue properties take ORE Studio's vocabulary, by the product
  owner's requirement that compass's HTTP and MCP align with ORE Studio's:
  each is a member of =route_catalogue= in ORE Studio's
  =ores.http.api/domain/route.hpp=, whose gate refuses a route without a
  tool, an area and an entity. The investigation's =:mcp_tool:=,
  =:mcp_title:= and =:read_only:= became =:tool:=, =:summary:= and
  =:writes:=. Every request has a tool, so sync also has a route; the area is
  =documents=, and the entities are =document=, =environment=, =service=,
  =sprint= and =campaign=.

* Notes

** What loads

In compass's own checkout the codegen codec is off, as the entity models
found, so =compass-ng check= reads these models only as documents and
nothing is written into compass's tree.
[[file:evidence/service_model_load_probe.sh][evidence/service_model_load_probe.sh]]
loads each model on a scratch copy of ORE Studio, in three stages.

| Stage | Change to the models | Result for all 3 |
|-------+----------------------+------------------|
| =as_written= | None. | Skipped without a word: =masd.codegen.operation= is not a codegen type. No output, no warning. |
| =ores_type= | =#+type: ores.codegen.operation=. | Loads with no error or warning. Writes the C++ protocol header and its TypeScript twin. The header's structs are the messages member for member, in =namespace compass::db::types=, with the =* Includes= block's headers. |
| =facets_on= | Also ORE Studio's protocol, wire codec and HTTP route facets on, and =:http_route: true= on each routed request. | Loads. Adds the JSON wire codec, its round-trip tests, a route file and a Hurl recipe page. The route file registers 0 endpoints and the recipe page lists none, because ORE Studio's route needs a NATS =:subject:=. No =/v1/= path and no MCP text reaches any output. |

** What compass's loader does not understand yet

The loader reads a message's =:subject:=, =:response:=, =:auth:=,
=:destructive:=, =:http_route:=, =:rate_policy:=, =:shell_command:=,
=:request_timeout_seconds:= and =:shell_adopts_token_for:=, and a field's
=:cpp_type:= and =:default:= (=projects/compass.model/src/ops/messages.cpp=,
=declared_messages=). It drops every other property without a word. This
list is the input to [[id:E754BE53-3A6B-4491-BB26-450D1A34F159][Generate JSON codecs]]
and [[id:8CF40A62-82EB-4FE0-8CEC-2621BD0E66FE][Generate the HTTP and MCP service]].

| What | Where | What happens today |
|------+-------+--------------------|
| =#+type: masd.codegen.operation= | header | Not in the codec's list of codegen types; the page is skipped. |
| =:http_method:=, =:http_path:= | request | Dropped. A route is only made from a =:subject:=, as =POST /api/v1/<subject>=; without one the route file registers nothing. |
| =:tool:=, =:area:=, =:entity:=, =:writes:=, =:summary:= | request | Dropped. Nothing generates a catalogue place or an MCP tool. |
| =:caller:= | request | Dropped. The only access property is =:auth:=, a session. |
| =:http_in:=, =:http_name:= | field | Dropped. |
| =:values:= | field | Dropped. =scenario_state=, =step_outcome= and =run_outcome= are used and never declared, in C++ and in TypeScript, so the outputs do not compile. |
| Prose under a message or a field | body | Not read. The loader reads only a =#+begin_src ... :name comment= block, a Doxygen comment, so the MCP descriptions have no source. |
| No =#+subcomponent:= | header | The route includes =ores.serve./messaging/...=, an empty part, where a simple component has none. |
| A message-typed field bound from the query | =filter= of three requests | Nothing defines it: the probe shows no binding at all. The models say each member becomes a parameter, and =keyword= and =property= carry =name:value=. |
| Binary =bytes= | =attach_request= | The wire codec writes a =std::string= as a JSON string; the bytes need base64 or a raw body. |

** Departures from the design and the investigation

- Catalogue vocabulary. The product owner required compass's HTTP and MCP to
  align with ORE Studio's, so the investigation's =:mcp_tool:=,
  =:mcp_title:= and =:read_only:= are ORE Studio's =:tool:=, =:summary:= and
  =:writes:=, with =:area:= and =:entity:= added. Every request has a tool,
  as every route has in ORE Studio. The design's MCP list is narrower: it
  names neither =facets=, =list_environments= and =version= nor the campaign
  writes. Which tools =/mcp= lists is left to the service task.
- Sync has a route, =POST /v1/{environment}/sync=, where the design made it
  an MCP tool only, because a tool is a route's catalogue name.
- The step, finish, note and address routes start at their row,
  =/v1/runs/{run}/...=, =/v1/campaigns/{campaign}/notes= and
  =/v1/notes/{note}=. The design puts the environment first, but those
  requests carry none: a run, a campaign and a note each belong to one
  environment already.
- =finish_run_request= has a route the design's table does not list.
- C++'s one =sprint_request= is two messages, because a message states one
  route. =add_note_response= wraps the bare id =query::add_note= answers.
- The messages state =#+namespace: compass::db::types=, where the query
  functions take them today, while the models sit in =compass.serve=. The
  codegen writes a model's outputs under its own component: before the
  messages are generated, either the queries move to =compass.serve=, as the
  design placed them, or the protocol facet writes into =compass.db=.
