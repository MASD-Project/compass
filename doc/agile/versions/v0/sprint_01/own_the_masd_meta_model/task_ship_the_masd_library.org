* Plan

The library lives in compass once, in =share/masd/=, and travels with the
binary that builds its contexts.

- *Where it is.* CMake installs =share/masd/= as =share/compass/masd/=
  beside =bin/=, so CPack carries it in the Linux tarball, the Windows zip
  and installer and the macOS image alike. Every build stages it at
  =publish/share/compass/masd/= beside =publish/bin/=.
  =build/scripts/install_compass.sh= lays the shared install out the same
  way, =~/.local/opt/compass/bin/= and =~/.local/opt/compass/share/compass/masd/=,
  and removes the binary and manifest of the older flat layout.
- *How it is found.* =@compass= in the codec's =library= option is
  =../share/compass/masd= from the directory of the running binary, which
  =platform::process::executable_path= resolves through links on Linux,
  macOS and Windows; the same rule serves the package, the build tree and
  the shared install.
- *How it layers.* =library= is a comma-separated list, searched in
  order. A template of a later directory replaces the one of the same name
  in an earlier one, so a project can override a MASD template. A data
  file and the catalogue come from the last directory that has them, so the
  licence is the project's. A node of the physical-space graph in two
  directories is an error, as the investigation recommends: a moved page
  cannot be left in both. ORE Studio writes
  =library=@compass,projects/ores.codegen/library=.
- *How a change is seen.* compass records no read outside the checkout,
  so a codec may now name an =environment= function whose bytes
  =configuration_hash= hashes with its code and options. codegen's is the
  path and content ID of every file of its libraries outside the checkout:
  an upgrade that changes a template, or an edit to a checkout's
  =share/masd= named by its absolute path, runs codegen again.
- *What it holds now.* One template, =cmake_component_root.mustache=, the
  root =CMakeLists.txt= of a component, which names nothing of ORE Studio.
  ORE Studio's copy of it still wins until task 3 deletes it, and renders
  the same bytes.

* Notes

** The layering rule

The brief asked that a template of a later directory override an earlier
one; the investigation and this page's acceptance ask that a node named
twice be an error. Both hold, for different files. A template is text a
project may want to restyle, and an override changes no output path. A node
decides which outputs exist; one left in two libraries after a move would
silently win or lose, so it stops the run instead. Data files and the
catalogue follow the templates: the last directory that has one wins, which
makes the licence the project's.

** Limits

- =component_files= still reads one =library= directory. Its two templates
  are ORE Studio's until task 3 moves them; it takes the list then.
- =origin=, which names the template behind a file for =diff= and
  =--scope=, cannot look into the checkout. With a checkout library listed
  after =@compass=, it names the checkout library's template even when only
  =@compass= holds it. ORE Studio's labels are unchanged; task 3, which
  makes templates live in =@compass= alone, is when it matters.
- The Windows zip and installer and the macOS image are built by the
  nightly workflows through CPack; the =install(DIRECTORY)= rule is the same
  for every generator, but only the Linux tarball was built and opened
  here.
