A point-in-time record, written while the story that commissioned it was open, of an [[id:A7F8D9E2-3C4B-4A5D-B67C-8E9F0A1B2C3D][investigation]] into how compass would generate its own database tables, migrations, row types and HTTP and MCP service from models, which of ORE Studio's meta model and templates are MASD and which are ORE Studio's own, how ORE Studio reads the meta model from compass once it moves, and the order of the work.

It is a snapshot, not a description of the system. Whatever it concludes that the code must keep doing belongs on the page that owns the subject; cite that page from code, recipes and models, not this one.

* Context

The story [[id:E3C81059-FE00-4403-AA56-190FDBB9904A][Own the MASD meta model and generate compass with it]] asks
compass to generate its own code with the generator it already runs on ORE
Studio. The first pull request of [[id:C1DC377F-4A1B-4131-B734-FE28DB63CF03][Serve the documents]],
[[https://github.com/MASD-Project/compass/pull/176][#176]], wrote compass's
database by hand: one migration that creates the schemas =corpus=, =test= and
=activity= (=projects/compass.db/src/ops/migrations.cpp=), the bookkeeping
schema =compass=, the row types of =projects/compass.db/include/compass.db/types/=
and the COPY staging in =src/io/corpus.cpp=. The product owner wants those
tables, and the HTTP and MCP service that will sit on them, generated from
models in compass's repository, and is most interested in how the tables
would be generated.

The questions were:

1. How would compass generate its own tables and row types, shown on two real
   tables, =corpus.document= and =activity.run=?
2. How does a generated schema evolve when the database holds activity that
   must survive an upgrade?
3. How would compass generate its HTTP and MCP service?
4. Which of ORE Studio's =projects/modeling= pages and template families are
   MASD, and which are ORE Studio's own?
5. How does ORE Studio read the meta model from compass once it moves?
6. In what order should the work go?

* Paths taken

** Generating compass's tables with ORE Studio's entity templates

The first path was the obvious one: write compass's tables as ORE Studio
entity models and let the templates that generate ORE Studio's 766 models
generate them too.

*** How ORE Studio generates a table today

A table in ORE Studio is a model page of =#+type: ores.codegen.entity= under
a component's =modeling/= directory. Its drawers and headings carry the
structure: =* Columns= (one heading per column, with =:type:= in SQL,
=:cpp_type:=, =:nullable:=, =:default:=, =:primary_key:=), =* Foreign keys=,
=* SQL ** Flags= (=:tablename:=), =* SQL ** Checks= and =* SQL ** Indexes=
(=name=, =columns=, =unique=, =current_only=, =where_extra=, =using=). Its
=* Flags= drawer binds a profile, such as =read-only-current-state=, which
fixes a set of features (=read_only=, =current_state=). Features change what
the context holds; the physical-space graph (the =ores.<space>.<facet>.org=
and =ores.<space>.<facet>.<archetype>.org= node pages of
=projects/ores.codegen/library/templates/=) decides which archetypes render,
and each archetype names one =.mustache= template and an output path. An
entity's model drawer and its profile can switch any address of the graph on
or off (=:ores.cpp.http-route.enabled: true=).

compass's codec runs the same pipeline in C++: =ops::generate_model= loads a
model, =entity_context= and its 25 =entity_*.cpp= steps build what
ores.codegen's Python built, =ops::model_units= lists the archetypes, and
=ops::render_output= renders each one. It writes all 26,212 outputs of ORE
Studio byte for byte.

*** What the probe shows

Measured on the two renders:

- *Schemas do not exist.* ORE Studio puts every table in =public= and spells
  the component into the name (=ores_<component>_<plural>_tbl=). The model's
  =:schema:= flag is read by nothing that renders: the create template quotes
  =sql_name_base= whole, so =corpus.document= became a table called
  ="corpus.document_tbl"= in =public=, while the unquoted trigger function
  landed in =corpus=, and =create trigger corpus.document_insert_trg= is not
  valid SQL, as a trigger takes no schema. The repository row hard-codes
  =schema = "public"= (=cpp_domain_type_entity.hpp.mustache=, line 39).
- *Only four key types reach C++.* The repository entity template declares a
  primary-key member for =uuid=, =timestamp=, =integer= and =text= only. A
  =bytea= key (the content hash) and a =bigint= key (the identity) render no
  member at all, while =columns()= still binds =&e::hash= and =&e::id=, so
  neither row compiles.
- *Identity is not a default.* The model has no way to say =generated always
  as identity=; stating it as =:default:= renders =default generated always as
  identity=, which PostgreSQL rejects.
- *Foreign keys assume a tenant.* With =:has_tenant_id: false= the enforced
  key still renders =("tenant_id", "campaign")=, because the target table is
  not an ORE Studio entity the registry knows.
- *Nullability does not reach the domain class.* =org_id= is =std::string=
  in the domain class and =std::optional<std::string>= in the repository row,
  because the domain class reads =:cpp_type:= as written.
- *The surface is ORE Studio's.* A table that nothing outside the database
  writes still gets an empty insert trigger, a NOTIFY trigger, NATS messaging
  and TypeScript. Profiles can withdraw them (=sql-only-store= withdraws
  =ores.cpp=, =ores.ts= and =ores.doc=), but what is left targets
  =ores.database='s query builder, =ores.logging= and =ores.utility=, none of
  which compass has. compass's database code is a thin RAII wrapper over
  libpq with COPY (=compass.db/io/connection.hpp=,
  =compass.db/ops/copy_text.hpp=).
- *What does work.* =text[]=, =jsonb=, =bytea= and =timestamptz= pass
  through to the DDL as written, the =now()= and ='{}'= defaults render, the
  =gin= index renders from the indexes table, and the outcome check renders
  from =* SQL ** Checks=.

Across the library, 44 of the 176 templates name =tenant_id=, 43 name NATS,
42 include =ores.utility=, 23 =ores.database=, 24 call =ores_utility_*= or
=ores_iam_*= SQL functions and 11 name =party_id=. The create template alone
is 1,263 lines, most of them bi-temporal history, tenancy, row-level security
and insert-time validation.

This path was set aside. ORE Studio's entity templates generate ORE Studio's
house shape, and bending 1,263 lines of it to produce a plain table would
make the template carry two products. The mechanism under them (model pages,
profiles, features, the physical-space graph, the codec) is what compass
should reuse.

** Generating them with a MASD table space

The second path keeps the mechanism and the entity model's structure, and
adds a small technical space for plain PostgreSQL and libpq that compass
owns: =masd.sql= and =masd.cpp=. compass's tables bind it; ORE Studio's keep
=ores.sql= and =ores.cpp=. The worked examples below are what a compass
developer would write and what the new templates must produce. The outputs
are the SQL of migration 1 and the C++ of #176, which is the specification
the templates are written to, not something any template renders yet.

The profile =content-addressed-row= fixes =read_only= (no update is ever
generated), =current_state= (no history columns) and =insert_conflict:
do_nothing=. The features it relies on, beyond those ORE Studio has:

| Feature      | Where       | Values                                      | Effect                                                                                                    |
|--------------+-------------+---------------------------------------------+-----------------------------------------------------------------------------------------------------------|
| =schema=     | entity      | an identifier                               | Qualifies every name: =corpus.document=, =document_org_id=. Exists in ORE Studio's models, read by no template. |
| =key_kind=   | key column  | =natural=, =content_hash=, =identity=, =ord= | =content_hash=: the key is the aggregate's identity, so the row omits it and the writer takes it as an argument. =identity=: =GENERATED ALWAYS AS IDENTITY=, read back, never written. =ord=: the row's place in its parent's vector. |
| =written_by= | column      | =database=                                  | The column has a default and is in neither the row type nor the COPY column list.                         |
| =opclass=    | index row   | an operator class                           | =USING gin (keywords jsonb_path_ops)=.                                                                    |
| =where=      | index row   | an expression                               | A partial index. ORE Studio's =where_extra= is the same thing appended to its validity predicate.         |

*** Which pieces exist and which must be written

| Piece                                                                 | State                                                                                                   |
|-----------------------------------------------------------------------+---------------------------------------------------------------------------------------------------------|
| Model page format: =* Columns=, =* Foreign keys=, =* SQL ** Indexes=, =** Checks= | Exists (ORE Studio's entity model, which compass's codec loads).                                    |
| Profiles and features, bound in =* Flags=, overriding graph addresses | Exists.                                                                                                 |
| Physical-space graph, archetype output paths, enablement               | Exists (=ops::load_physical_space=, =ops::model_units=).                                               |
| Codec: facts, incremental regeneration, =compass generate=, =diff=, =check= drift | Exists.                                                                                      |
| =text[]=, =jsonb=, =bytea=, =timestamptz=, defaults, gin indexes, table checks in DDL | Exist as pass-through text in ORE Studio's DDL; the new template keeps that.                |
| Schema-qualified names (=:schema:=)                                   | Must be written: read by no template today.                                                            |
| =key_kind=: content hash, identity, ord; composite keys =(hash, ord)= | Must be written. ORE Studio's junction has a composite key; its entity does not, and its C++ maps four key types. |
| =written_by: database=, =values=, =opclass=, =on_delete=              | Must be written.                                                                                        |
| =tsvector=                                                            | Type passes through; the column is =computed=: =corpus.section.tsv= is filled from the document's title and a configured =regconfig= in #176's insert, which a generated column cannot do, as it may read neither another table nor a setting. ** Migrating a generated schema

ORE Studio never migrates. Its =projects/ores.sql/modeling/component_overview.org=
states the policy: a schema change edits the =create/= scripts and the database
is destroyed and recreated with =compass db recreate=, and
=schema_fingerprint.cmake= stamps a hash of the SQL into the database so a
binary refuses a database built from other scripts. That suits a database whose
contents are reloaded from reference data. compass's is not one: the corpus can
be synced again, but =activity= holds test runs, notes and attachments that
exist nowhere else until they are exported. #176 therefore already has
versioned migrations: =ops::migrations()= lists them from 1 with no gap,
=compass.migration= records the ones applied, =compass db migrate= applies the
missing ones under an advisory lock, and a released migration is never edited.

Four ways a generated schema could evolve:

| Way                                                   | Keeps activity | Renames and data moves                         | Cost                                                                                     |
|-------------------------------------------------------+----------------+------------------------------------------------+------------------------------------------------------------------------------------------|
| Recreate, as ORE Studio does                          | No             | Not needed                                     | None, and it loses every run.                                                            |
| Migrations generated by diffing two model versions    | Yes            | Cannot tell a rename from a drop and an add; cannot move data | A model differ and a DDL differ, both of them guessing.                         |
| Declarative apply by an external tool (diff the live database against the target) | Yes | Same ambiguity, decided at run time on the user's database | A new dependency on every machine that runs =compass db migrate=. |
| Versioned generated DDL with hand-written deltas      | Yes            | Written by the person who knows what changed  | One delta per release that changes the schema, and one test.                             |

The recommendation is the last one, in this shape:

- The models generate =projects/compass.db/sql/schema.sql=, the whole schema
  at the current version, as one output of the codec. It is never run against
  an existing database. Its =git diff= in a pull request is the specification
  of the delta that pull request must add.
- Migrations stay as #176 has them, one SQL text per version, hand-written in
  =projects/compass.db/sql/migrations/NNNN_<name>.sql= and frozen once
  released. Migration 1 is a copy of the generated =schema.sql= at the first
  release that creates a database; since #176 has not been released, its
  hand-written migration 1 is replaced, not followed by a delta.
- A database test applies every migration to one empty database, runs
  =schema.sql= on another, and compares the two catalogs (tables, columns and
  their types, defaults and nullability, constraints, indexes). A model change
  without its delta fails it, and so does a delta that does more than the
  model says. =compass.testing='s =scoped_cluster= already gives the test its
  databases.
- The profile =activity-record= marks its tables =retained=. The codec
  reports a model change that removes or retypes a column of a retained table
  unless the same pull request adds a migration, so the person who drops a
  column has written down what happens to its data.

This keeps generated code generated and puts the one judgement a generator
cannot make, what an old row becomes, in a file a reviewer reads.

** Generating the HTTP and MCP service

*** What ORE Studio generates

ORE Studio generates HTTP routes from models, and has a model type for
operations that are not CRUD on an entity:

- The facet =ores.cpp.http-route= (=#+model_types: domain_entity junction
  operation=, disabled by default) is switched on per model with
  =:ores.cpp.http-route.enabled: true=. An entity gets its CRUD verbs
  (=GET /api/v1/<component>/<plural>=, =GET .../<key>=, =POST
  .../get-many=, =POST= and =PUT=, =DELETE=, =.../versions=). An
  =ores.codegen.operation= model gets a route for each message that states
  =:http_route: true=.
- =projects/ores.iam/modeling/ores.iam.session_statistics_operations.org= is
  such a model: a parameterised query whose request message has typed fields
  with defaults. Its generated route,
  =projects/ores.http/iam/src/routes/iam/session_statistics_operations_routes.cpp=,
  is a forwarder:

  #+begin_src cpp
  auto get_session_statistics_route =
      router->post("/api/v1/iam/ops/get_session_statistics")
          .summary("Get session statistics")
          .auth_required()
          .body<messaging::get_session_statistics_request>()
          .response<messaging::get_session_statistics_response>()
          .handler([&session](const http_request& req) {
              return handle_get_session_statistics(req, session); });
  #+end_src

  The handler parses the JSON body and calls
  =ores::http::forwarding::respond=, which sends the request on the message's
  NATS subject with the caller's token. The verb is always =POST= and the
  path is the subject transliterated; compass already ports that projection
  (=write_operation_http_route=,
  =projects/compass.codegen/src/ops/template_context.cpp=).
- Beside the route the same model generates the protocol structs
  (=ores.cpp.protocol=), their JSON and MessagePack codec
  (=ores.cpp.wire-codec=), a Hurl recipe (=ores.doc.http-recipe=) and a shell
  command.
- Hand-written: the service-side handler of an operation (permission checks
  such as =has_permission(req_ctx, "iam::sessions:read")= and the SQL), and
  the whole server, =ores.http.api=, about 6,200 lines on Boost.Beast with
  coroutines, JWT sessions and an OpenAPI 3.0 document built at run time from
  the registered routes.
- =service_registry.org= models deployment and database access (roles,
  grants, replicas), not endpoints. =service_facet.org= is the scaffold of a
  NATS service's host, configuration and =main=. =http_facet.org= still says
  no codegen profile exists for the HTTP layer, which the facet page and its
  outputs contradict.
- MCP is not generated. ORE Studio's MCP server is hand-written TypeScript
  (=projects/ores.agent/src/mcp.ts=, =src/tools.ts=).

None of the route templates fits compass. The design of Serve the documents
([[id:21C1D3CC-9EE3-48C3-8EDD-BA0C16032AB2][Design: the document service]])
calls the query layer in process, reads the caller's view and name from
gateway headers, uses =GET= with path and query parameters, and has no NATS
and no JWT. compass has no HTTP, MCP or JSON code today: =vcpkg.json= lists
catch2, expat, pcre2, tree-sitter and zlib, and #176 adds libpq.

The route it would generate, one binding line per field, chosen by

#+begin_src cpp
void document_queries_routes::handle_search(const httplib::Request& req,
    httplib::Response& res, const query::document_queries& queries) {
    const auto caller = http::read_caller(req, http::caller_need::view);
    if (!caller)
        return http::refuse(res, caller.error());
    messaging::search_request r;
    if (const auto e = http::bind_path(req, "environment", r.environment))
        return http::refuse(res, *e);
    if (const auto e = http::bind_query(req, "q", r.q,
            http::presence::required))
        return http::refuse(res, *e);
    if (const auto e = http::bind_query(req, "type", r.type))
        return http::refuse(res, *e);
    if (const auto e = http::bind_query(req, "tag", r.tag))
        return http::refuse(res, *e);
    if (const auto e = http::bind_query(req, "limit", r.limit))
        return http::refuse(res, *e);
    http::answer(res, queries.search(*caller, r));
}

void document_queries_routes::register_routes(httplib::Server& server,
    const query::document_queries& queries) {
    server.Get("/v1/:environment/search",
        [&queries](const httplib::Request& req, httplib::Response& res) {
            handle_search(req, res, queries);
        });
}
#+end_src

** Reading the meta model from compass

The codec's =library= option is a directory relative to the checkout, read
through =ops::checkout_reader=, and the codec turns every template, the graph
and the licence into facts, so a changed template regenerates what it renders.
Once the MASD half lives in compass, ORE Studio needs it without a copy.

| Way                                                         | ORE Studio CI                                                             | Worktrees                                          | Windows and macOS                                     | Version skew                                                         |
|-------------------------------------------------------------+---------------------------------------------------------------------------+----------------------------------------------------+-------------------------------------------------------+----------------------------------------------------------------------|
| Installed share directory in the compass package            | Already installs the release =build/scripts/compass_ng.pin= names; the library comes in the same tarball. | Nothing to do: every worktree uses the installed compass. | CPack already builds ZIP, WIX, DragNDrop and TGZ; =share/= travels as =bin/= does. | None: the templates and the C++ that builds their contexts are one release. |
| Git submodule of compass in ORE Studio                       | Every workflow must check out submodules.                                 | Each of ORE Studio's many worktrees needs =git submodule update=. | Works, with the usual submodule friction.          | The submodule commit and the installed binary can disagree, and a template can need context a binary lacks. |
| A vcpkg or system package of the library alone               | A second pin.                                                             | Nothing to do.                                     | A port per platform.                                  | Two versions to keep in step.                                        |
| Copy, as today                                               | Works.                                                                    | Works.                                             | Works.                                                | The story forbids it.                                                |

The recommendation is the installed share directory:

- compass installs its MASD library to =<prefix>/share/compass/masd/=:
  templates, graph nodes, the meta model pages, the modelines. The release
  tarball, zip and installers carry it.
- The codec's =library= option takes a list, searched in order, and a
  library named =@compass= resolves against the running executable
  (=../share/compass/masd= from its =bin/=). ORE Studio's =.compass.org=
  becomes =library=@compass,projects/ores.codegen/library=: compass's nodes
  first, ORE Studio's facets, templates, profiles and licence added on top.
  A node named twice is an error, not an override, so a move cannot leave a
  page in both.
- The licence and the product root come from the project, not from the
  shared library: a project states its =product= (=ores=, =compass=) and its
  licence file in its own library.
- Reading outside the checkout needs a reader for the share directory; the
  facts already hash every template, so a compass upgrade that changes one
  regenerates what it renders and =compass check= reports it as drift.
- To work on the meta model against ORE Studio before a release,
  =--set codegen.library=<compass checkout>/share/masd,projects/ores.codegen/library=
  points at a checkout instead.
- ORE Studio's pages link to MASD pages by =id:=. compass's link checks must
  index the share directory's pages, or those links break when the pages
  leave ORE Studio.
- ORE Studio's output must not change by a byte. That is measurable before
  the move: render ORE Studio with the layered library and compare with the
  26,212 outputs, as the codec's port was measured.

* Conclusions

- *Tables.* compass can generate its tables with the machinery it already
  runs on ORE Studio: model pages, profiles, features, the physical-space
  graph and the codegen codec. It cannot use ORE Studio's table templates.
  Rendered on =corpus.document= and =activity.run=, they put the table in
  =public= under a quoted name with a dot in it, drop the =bytea= and =bigint=
  keys from the C++ row so it does not compile, render identity as a default,
  add a tenant to a foreign key of a table without one, and surround the
  table with NATS, TypeScript and ORE Studio's database library. compass needs
  a MASD entity context and four or five small templates for plain
  PostgreSQL and libpq, plus the features =schema=, =key_kind=, =written_by=,
  =values=, =opclass=, =on_delete=, =computed= and =generated=. Their target
  output is migration 1 and the row types of #176, which already exist, so
  the templates have a specification to meet byte for byte.
- *Migrations.* Recreating, as ORE Studio does, would lose test activity.
  Generated diffs between model versions cannot tell a rename from a drop or
  move data. Versioned generated DDL with hand-written, frozen deltas, held
  to the generated schema by a catalog comparison, keeps the activity and
  puts the one judgement a generator cannot make in a reviewed file.
- *Service.* ORE Studio generates HTTP routes from entity and operation
  models, but every route is a =POST= that forwards over NATS on ORE
  Studio's own Beast server, and it generates no MCP. The operation model
  type is the right input; it needs HTTP and MCP properties, and compass
  needs new route and MCP tool templates. The MCP tool descriptions come
  from the same message prose as the routes.
- *Classification.* Of ORE Studio's modeling pages, the variability
  features that describe structure (current state, read only, checks, keys,
  hierarchy, licences) and the theory pages are MASD; tenancy, parties, RLS,
  NATS, the Qt presentation bundle, the system model and finance are ORE
  Studio's. Most technical-space and facet pages, and most C++ and SQL
  template families, are Split: generic in concept, ORE Studio's in text.
  Every family is at least Split until the address root =ores= is a
  parameter, in ORE Studio's library and in compass's code alike.
- *Distribution.* The MASD library belongs in compass's package, versioned
  with the binary whose context builders it needs, layered under each
  project's own library.

Tasks 4 and 7 can run side by side once 3 lands. If the move is slow, 4 can
start after 1, writing its pages in compass from the start; the move then
has fewer pages to carry.

Search, meanwhile, should be the hand-written half that generation never
replaces. Write its queries as SQL in =compass.db= (a =query= namespace
beside =io/corpus=), behind a function per question:
=search(const caller&, const search_request&)= returning a =search_response=
of =search_hit= rows, named and shaped as the operation model above names
them, and measure it against the recorded questions in a test, with no HTTP.
It reads the tables only by their column names, which the generated schema
keeps, so task 5 does not touch it. When task 8 lands, the generated route
and MCP tool call that function and the hand-written structs are deleted in
favour of the generated messages. Search should not build a route, a JSON
encoder or an MCP handler of its own: that is exactly the code task 8
generates, and a hand-written copy would be thrown away.

Durable conclusions belong on the pages that own them once the tasks run:
the migration policy on =compass.db='s component overview, the features and
profiles on their own pages in compass's library, and the classification on
the meta model's index page.
