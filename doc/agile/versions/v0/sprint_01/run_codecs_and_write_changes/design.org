The interface, the registry, the runner and two codecs are implemented and
run over this repository and over ORE Studio. Dependency recording is built:
the view records what each unit reads and a run calls only the units whose
inputs changed. Changed-only writes are built: an output sink writes a file
only when its content changed and restores generated files edited by hand.
Diff mode is built: the sink plans before it writes, and a diff run prints
the plan and writes nothing. The result cache is built: a unit no record
stands in for is looked up in a cache every worktree of the repository
shares, by a key that needs no inputs, before it runs. Every part this page
argued for is built; the compass.codec overview describes them as they are.

* Summary

A codec is a =descriptor= and one function. The descriptor is constant data:
name, version, the document types read, options with defaults, rules, and
whether the codec runs by default. The function has one of four types. Its
type says whether one call works on a document or on the whole corpus, and
whether it emits files or diagnostics.

A codec reads through a =corpus_view= that numbers only the documents of the
types it declared. It appends to a struct-of-arrays table: =file_table= (path,
bytes) or =diagnostic_table= (document, source range, rule, severity, message,
fix). It never opens a file and never writes one.

=make_registry= resolves the descriptors against the type registry and applies
the configuration. =run= runs the enabled codecs in parallel. Neither knows a
codec by name.

* What the interface must do

Every later feature is a codec: code generation, HTML export, the gates,
analysis reports. The next four tasks of this story and the gates story put
these demands on the interface, and no codec may need to change to meet them.

1. /Record dependencies./ The runner must know what each codec read, down to
   the document, so a change re-runs only the codecs that read it.
2. /Write only changed outputs./ The runner must hold every output before
   anything reaches the disk.
3. /Diff mode./ The same run must be able to end in a diff with no write.
4. /Cache results./ A result must be a pure function of the codec's version,
   its configuration and the content it read, so another worktree can reuse
   it.
5. /Gates./ A diagnostic must be comparable across two commits (ratchet), must
   be matchable to an exception written in the document, and must name its
   fix. The rules a codec enforces must be listable without running it.
6. /Speed./ All ported gates over ORE Studio in under 10 seconds, and a verdict
   on an edit in under one second.

* The codec

** The descriptor is data

#+begin_src c++
struct descriptor {
    std::string_view name;
    std::uint32_t version = 0;
    std::string_view summary;
    inputs reads;
    std::span<const option> options;
    std::span<const rule> rules;
    bool enabled_by_default = true;
    codec_function run;
};
#+end_src

Everything the runner, the cache and the rule table need is readable without
calling the codec. =version= is bumped by hand, as =parser_version= is, when
some input would give a different output. =options= declares each key with its
default, so the effective configuration of a codec is a fixed list of values
in a fixed order, which is what a cache key needs. =rules= gives each rule a
name and a summary; the gates story generates its rule table from it.

=reads= is a list of =#+type:= values, every registered type, or every
document. The names are resolved once, when the registry is built, into one
flag per row of the type registry plus one for documents with no registered
type. A name the registry does not hold is a problem the registry reports,
and the codec still runs over the types that resolved.

** The function type states the unit and the output

#+begin_src c++
template <typename Output>
using document_function = void (*)(const document&, const corpus_view&, Output&);
template <typename Output>
using corpus_function = void (*)(const corpus_view&, Output&);

using codec_function = std::variant<
    document_function<file_table>, document_function<diagnostic_table>,
    corpus_function<file_table>, corpus_function<diagnostic_table>>;
#+end_src

A /document codec/ is called once per visible document. A /corpus codec/ is
called once. The unit and the output kind are not fields that could disagree
with the function: they are read from its type. A files codec has no table to
put a diagnostic in.

A function reads only its arguments and writes only its output table. That is
the whole contract, and it is what lets the runner call it on any thread, skip
the call when a cached result exists, and throw the output away in diff mode.

* The view

=corpus_view= holds the corpus rows of the documents whose type the codec
declared and numbers them from zero. =view[i]= returns a =document=: corpus
row, path, content ID (the git blob ID), type, source bytes and tables. A
document of another type has no number, so a codec cannot name it. The view
also gives the type registry and =option(key)=.

Every read of a document goes through =operator[]=, =find_id= or
=find_path=, and those are the hooks for dependency recording. Each piece of
work the runner starts copies the codec's view and points it at the log of
the unit it is calling, so a log is written by one thread and needs no
lock.

* The outputs

=file_table= is two byte-string columns, paths and contents. =diagnostic_table=
is four fixed-width columns and two byte-string columns. Both append in O(1)
and concatenate with one offset shift, which is how the runner joins the
tables of the pieces of one codec.

A diagnostic names its document by corpus row, not by path: the row is four
bytes, and whoever reports the finding has the corpus. Its =range= is a byte
range in the source. Its =rule= is an index into the descriptor's rules, so a
finding cannot carry a rule nobody declared. Its =message= must be stable: no
line number, no count, nothing an unrelated edit changes. Its =fix= is a
separate column, so a tool can show or apply it without parsing the message.

* The registry and the runner

=make_registry= takes a span of descriptors, the type registry and the
configuration, which is rows of (codec, key, value). The key =enabled= turns a
codec on or off; any other key must be a declared option. The set of codecs is
the span the host passes: =codecs::catalogue()= plus the codecs of any other
component. Nothing registers itself.

=run= builds, per enabled codec, the visible rows and a view. A corpus codec
is one piece of work. A document codec is cut into contiguous runs of
documents, four per thread. Threads take pieces from a shared counter. Each
piece fills its own tables, and the tables of a codec are joined in piece
order, so the result is identical on one thread and on eight. A test pins
that. No codec reads what another emits, so there is no order to respect
between codecs.

* How the later work attaches

** Dependency recording, and a codec that needs other documents

Two statements about what a codec reads exist, and both are needed.

The /declaration/ in the descriptor is static. It bounds what can ever affect
the codec: a change to a document of an undeclared type cannot, and the
runner can know that without running anything. It is also the only statement
available before the first run.

The /record/ is dynamic, as a compiler's dependency file is. It narrows the
declaration to what a call did read.

- A document codec called for document A that reads nothing else records
  {A}. Changing B does not re-run it for A.
- A corpus codec that walks the view records the walk: the set of visible
  (path, content ID) pairs. Any change in the declared types re-runs it.
- A codec that needs another document, such as HTML export printing the title
  of a link target, asks the view for it: =view.find_id(id)= or
  =view.find_path(path)=. The view records the question and the answer,
  including "no such document". A document that appears later with that ID
  then re-runs the codec for A, which a list of documents read could not
  express.

So a codec that needs other documents declares their types in =reads=, and
reaches them only through the view. Today every declared type is also a type
a document codec is called for. HTML export will be called for every document
and may look up any document, so one set serves it. A codec that is called
for tasks and looks up stories needs two sets; that becomes a second =inputs=
field, =references=, empty by default. A new field with a default and a new
method on the view change no existing codec.

** The record as built

The recording task built the record this way.

- /Inputs./ A document handed out is a =path= input: its path as the key and
  its content ID as the value. A =find_id= is an =id= input whose value is
  the blob ID of the path found, so it changes when another document takes
  the ID; the document found is also a =path= input. A =find_path= is a
  =path= input. A miss has =found= 0. A call of =types()= is a
  =type_registry= input with the SHA-1 of the registry's tables, which is
  what re-runs =required_sections= when a contract changes its required
  sections. A corpus unit records one =type_set= input, the SHA-1 of the
  sorted paths and content IDs of every document it may read, and nothing
  else about documents: every answer it could get is a function of that set.
- /The path of a document is a recorded read./ Every document input is keyed
  by path, so a codec that reads =document.path= depends on it without an
  accessor, and a rename is a new unit. The question in Least certain below
  is settled this way.
- /Key./ A unit is named by codec and document path and is reused when the
  codec's version and configuration hash equal the recorded ones and every
  input has the recorded answer. Answers are computed by the same functions
  for the view and for the check, so they cannot disagree.
- /Outputs live in the record./ Each file is kept with its path, blob ID and
  bytes; findings are kept encoded with their document as a path, with
  their count and SHA-1. A skipped unit's outputs are put into the
  =run_result= where the call's would have been, so the writer task gets a
  complete result either way. The store was the alternative: collection
  removes any object that no git index or worktree index names, so a skipped
  unit's output could vanish between runs and the runner would need a
  fallback to call it again. The cache task, which shares results across
  worktrees, is where outputs move into the store with a root that keeps
  them live.
- /File./ =<git dir>/compass/deps=, beside the worktree index: magic
  =CMPSDEP\n=, version, the units, a SHA-1 trailer. It is written by
  temporary file and rename and only when its bytes change. A damaged file,
  or one of another version, is ignored and every unit runs.
- /Disabled codecs/ are not in the record of a run, so re-enabling a codec
  runs all its units once.

** Write only changed outputs, and diff mode

The runner holds every output as bytes before any reaches the disk. Writing
only what changed is a comparison of each content hash with the recorded one.
Diff mode is the same run with a different last step. Removing an output that
a codec no longer emits needs a record of what each codec emitted last time;
that record belongs to the runner.

** The sink as built

The writing task built it this way.

- /Where./ =io::write_outputs= in =compass.codec=, with its record types in
  =types= and the pure parts (=outputs_of=, =check_outputs=, the record
  encoding) in =ops=. The sink reads codec outputs and its record sits
  beside the dependency record, so it belongs with the runtime.
  =compass.store= sits below the codecs and knows nothing of them, and a
  component of its own would have one host and one function.
- /Input./ =types::output_set=: per file the codec, the path relative to
  the output root, the bytes and the blob ID, plus the names of the
  /complete/ codecs. =ops::outputs_of= takes the files and hashes from the
  run's dependency record, which already holds them in run order. Every
  enabled codec is complete, because a skipped unit's outputs come from the
  record; a disabled codec is not, so its files stay.
- /Refusals first./ A path that is absolute, empty, or has an empty, =.= or
  =..= component, or a path two rows produce, is a problem, and nothing is
  written when there is one. A path that passes through a directory under
  the root that is a symbolic link is also refused, since the link could
  send the write outside the root; a removal through one is skipped and its
  file kept. A final component that is a link is replaced by the rename,
  never written through.
- /Decision per output./ When the recorded entry has the same blob ID and
  the file's stat data equals the recorded stat data and is not racily
  clean, the file is not opened. Otherwise an existing file is hashed and
  left alone when it holds the bytes. Only then is it written, by temporary
  file and rename, and stat'ed. So a lost or damaged record costs a read of
  every output, not a write, and the build sees no change.
- /Counts./ written (new bytes for the path), restored (bytes compass wrote
  before, put back after an edit or a deletion), unchanged, removed, and
  kept: a recorded file of a complete codec that no output names is removed
  only when it still holds what compass wrote, with the directories the
  removal empties up to the root. One edited since is left in place and
  dropped from the record. The plan said only that files compass never wrote
  are never touched; a generated file someone has since edited is treated
  the same way, because removing it would lose the edit.
- /Racy entries./ Stat data says nothing about an edit made in the same
  clock tick as compass's write. The record keeps =written=, the start of
  the run that last changed it, and an entry modified in that second or
  later is compared by content, as git and the worktree index do. Every
  file a run writes is racy for the next run, which hashes it and moves
  =written= on, so the record is rewritten once more after a write and is
  then stable.
- /Record./ =<git dir>/compass/outputs=: magic =CMPSOUT\n=, version, entry
  count, written time, root, then per path (sorted) the codec, blob ID and
  the nine stat fields git keeps, and a SHA-1 trailer. It is written by
  temporary file and rename, only when its bytes change. A damaged file, one
  of another version, or one whose path is not plain relative is ignored. A
  record of another root is ignored too, so pointing =--write= somewhere new
  writes there and removes nothing.

** Diff mode as built

The diff task built it this way.

- /One decision./ The sink splits into =io::plan_outputs=, which reads the
  root and returns an action table (path, codec, action, new bytes) with the
  record for the next run, and =io::apply_outputs=, which performs it.
  =write_outputs= is the two in turn and its tests pass unchanged. A diff
  prints the plan a write would apply, so the two cannot disagree. The
  record's written time is decided in the plan: a write or restore always
  changes an entry, since the rename gives the file a new inode.
- /The diff./ =ops::unified_diff= in process: Myers' O(ND) algorithm in
  linear space (middle snake, then the two halves), in git's format with
  three lines of context. Its tests run =git diff --no-index= on each case
  and require the same bytes from the =---= line on. The headers carry no
  =diff --git= or =index= line, since those need modes and hashes a review
  does not. git's slider heuristics are not reproduced, so a change among
  repeated lines can be placed differently, though no longer.
- /Nothing written, by construction./ The =codecs= stage splits into
  =evaluate=, which loads the corpus and runs the codecs and only reads, and
  =persist=, its one writer: parsed objects, the worktree index, the
  dependency record, the outputs and their record. A file whose object is
  missing is parsed into memory and its object is stored by =persist=, so
  the store is untouched too. =diff_codecs_stage= calls =evaluate= and the
  plan and never =persist=. The tests snapshot every file under the
  checkout, its git directory and the store, bytes and times, around a diff.
- /The command./ =compass-bench codecs --diff <root>= prints the diff on
  standard output, so it can be piped, and the summary (would write,
  restore, remove, keep) on standard error. It exits 0 when nothing would
  change, 1 when a file would be written, restored or removed, and 2 when
  the run fails, as =diff(1)= does. A keep changes no file and so does not
  count. =--write= and =--diff= together are a usage error.

** The result cache

The key of a result is the codec's name and version, its option values in
declared order, and what the record says it read. For a document codec the
unit of caching is one document, so an edit to one of ORE Studio's 10,917
documents re-runs one call of each document codec.

A cached result must not hold a corpus row, because rows differ between
worktrees. The cache will store a diagnostic's document as the position of
the read it refers to, and resolve it on load.

** The result cache as built

The cache task built it this way.

- /Two levels, as ccache's direct mode./ The plan let a unit with no record
  in this worktree run once to learn its inputs. The cache instead looks a
  unit up by what is known before it runs. The /manifest key/ is the SHA-1
  of the format version, the codec's name, version and configuration hash,
  and the unit's identity: its document's path and content ID, or, for a
  corpus unit, an empty path and its type set hash. The manifest lists up to
  eight input sets, newest first, each the inputs one call read, in its
  record's order, with the key of the result it produced. The first set
  whose every input has the same answer now, misses included, names the
  /result/: its key is the SHA-1 of the manifest key and the inputs sorted
  by kind and key, and its body the unit's files and encoded findings.
- /The path is part of the identity./ The plan named the content ID alone.
  Two documents with the same bytes then share a manifest, and in a
  worktree that has both, the set one wrote holds for the other, which
  takes its findings. For the same reason the result key holds the manifest
  key and not only the inputs: a unit for A that reads B and a unit for B
  that reads A read the same set. A test pins the first case.
- /Findings by path./ A result holds its findings encoded as the record
  holds them, each document named by path; the corpus index resolves them
  on load, and a result naming a document the corpus lacks is a miss.
- /Equal to a run with no cache./ A hit's files and findings go into the
  result where the call's would, and its row into the record with the
  matched set as its inputs. The tests compare outputs and record bytes
  with a run that has no cache; on ORE Studio the two worktrees' records are
  the same file byte for byte.
- /Storage./ Generic in =compass.store=: an action object is named by its
  key, framed with the magic =CMPSACT\n= and a SHA-1 of key, magic and
  body, under =<git common dir>/compass/manifests= and =compass/results=,
  written by temporary file and rename. A damaged, truncated or misnamed
  object reads as missing. The keys and formats are =compass.codec='s
  (=ops/action_cache=), so the store still knows nothing of codecs.
- /Reads in the run, writes in persist./ =ops::run= takes an action source
  and only reads, on the run's threads. It returns the units it called;
  =io::store_actions= writes each one's result and puts its set first in
  its manifest, rewriting the manifest only when that changes it. A diff run
  still writes nothing. A result is always rewritten, so one whose damage
  made the unit run is replaced.
- /Liveness./ The dependency record (now version 2) names the manifest and
  result of every unit, ran, skipped or cached. Collection lists the action
  directories with the objects under one cap and grace period, and keeps an
  action object while any worktree's record names its key. The store asks a
  function for each worktree's keys, which the host fills with
  =io::action_keys=, so the dependency points from the codec runtime to the
  store and not back.
- /Outputs stay in the record./ The record still holds every output, so a
  run in one worktree with nothing changed reads one file and no action
  object. Moving them out would make the no-change run read 10,000 small
  files instead.

** Ratchet, exceptions and the rule table

- /Ratchet./ Two runs are compared as multisets of (document path, rule,
  message). That is why the message holds no position.
- /Inline exceptions./ An exception is written in the document and names
  =codec/rule=. The runner parses exceptions and drops the findings they
  cover, by document, rule and range. Codecs do not know exceptions exist. An
  expired or unapproved exception is a finding of a codec the runtime owns.
- /Rule table./ It is generated from =descriptor::rules=.

* The two codecs

=document_index= is a corpus codec that emits one file. The format is
tab-separated text with a header line, one line per document, in byte order
of the paths. An org table was the alternative. It needs its columns padded to
the widest cell, so one long title rewrites every line and the diff shows
nothing; a title with =|= needs escaping; and the file would be an org
document, so the next run would index its own output. A TSV line changes only
when its document does, and =cut= and =awk= read it.

=required_sections= is a document codec over every typed document. It reports
each section the type registry requires and no heading carries. The range is
the value of the =#+type:= keyword, the text that makes the section required.
The message is =task document has no "Plan" section= and the fix is =Add the
heading "* Plan"; the task contract requires it.=

The second run hashes the index because the first run wrote it in the

covered by the tests, not measured here: both codecs always produce their
outputs.

The second worktree ran no unit, and its process took half the time of the
first because its 10,917 objects were mapped from the store, not parsed. The
cache itself saves nothing here: the two codecs cost about 23 ms over all
threads, and 10,118 lookups read 20,236 small files in about 30 ms. A run
from the cache and a run that calls everything both take about 60 ms of
wall time, most of it building the record (hashing the 1.9 MB index and
encoding the findings). The cache pays for codecs that cost more per unit
than two file reads: code generation and the HTML export.

* Alternatives rejected

- *A virtual interface.* =class codec= with virtual =name()=, =version()=,
  =inputs()= and =run()=. The getters would return constants, and the runner
  needs those constants without an object: to list rules, to build a cache
  key, to select codecs by type. An object also invites state kept between
  calls, which breaks both parallel calls and caching. A descriptor is a
  value: it can be listed, compared, printed and built in a test with a
  lambda. The cost is the same, one indirect call per unit.
- *Learning a unit's inputs by running it.* The plan's first form: key the
  result by the inputs the record says a unit read, and run a unit with no
  record once. A fresh worktree would then run every unit to save nothing.
  The manifest gives the inputs before the run.
- *Content-only unit identity.* See The result cache as built.
- *Outputs in the store, the record holding hashes.* A smaller record, but
  a run with nothing changed would read one object per unit.
- *Self-registration.* A static object in each codec's file that adds itself
  to a global list. The set of codecs then depends on which object files the
  linker kept, and a static library drops the ones nothing refers to. The
  host passes the list instead.
- *Corpus invocation only.* Simple, and enough for the two codecs here. But
  the runner then sees one call that read everything: one edit re-runs HTML
  export for 10,917 documents and no result smaller than the corpus can be
  cached.
- *Document invocation only.* An index, a duplicate-ID check or a link graph
  needs all documents at once. Expressing them as a per-document step and a
  merge step is possible and is more machinery than a second function type.
  It can be added as a third type if a corpus codec proves too coarse.
- *A batch of documents per call.* One call with a span of subjects avoids a
  function call per document. A read can then not be attributed to one
  subject, so the record is per batch, and the measured cost of the call is
  nothing.
- *One output type with both tables.* A files codec could then emit a
  diagnostic, and whether that is legal would be a run-time check. Two table
  types make it a compile error. A generator that must report a bad model is
  a second codec, or a later decision to let files codecs emit both.
- *A sink callback per output.* =emit(path, bytes)= through a function. The
  table is the same data without the indirection, it concatenates, and it is
  what the cache stores.
- *Diagnostics that carry a path.* A string per finding, 4,751 times on ORE
  Studio, for something the reporter can look up from four bytes.
- *A typed options struct per codec.* Type-safe inside the codec. But the
  configuration file is not designed, the cache key needs one canonical form
  for every codec, and the runner would need a way to parse into a type it
  does not know. Options are strings; a codec parses its own.
- *Input types checked at each call.* Comparing type names per document per
  codec. They are resolved once into a flag row.
- *A content ID type of its own.* =compass.org= avoids =compass.store= by
  using a raw array. The codec runtime will write results to the store, so
  it uses =store::types::blob_id= and one type means one thing.
- *An org table for the index.* See The two codecs.
- *Writing every output on every run.* Simple, and it touches every
  modification time, so a build that depends on generated files rebuilds
  everything after any run.
- *Trusting the record alone.* Comparing hashes with the record and never
  looking at the disk misses a hand edit and a deleted file, and a lost
  record would rewrite every file. Stat data catches both at the cost of
  one lstat per output.
- *Removing every file under the root that no codec produces.* The root may
  hold files compass never wrote; only recorded paths are compass's.

* Least certain

- *The path is in every key.* A rename re-runs every unit that read the
  document, and the cache does not help: the path is in the manifest key.
  Dropping it needs the path behind an accessor, so a unit that never reads
  it records no path input.
- *The record holds the outputs.* 6 MB on ORE Studio, read and checked on
  every run, and the cache holds the same bytes again. The cache task kept
  them in the record (see The result cache as built).
- *Many small files.* 20,236 action objects on ORE Studio take 5.3 MB of
  bytes and about 81 MB of disk blocks, and a lookup is two file reads. A
  pack of action objects, or no caching for codecs cheaper than a lookup,
  would fix both.
- *Concurrent manifest writes.* Two worktrees that add a set to one
  manifest at once can lose one set; the unit then runs once more. No
  result is ever wrong, since a result is checked against its key.
- *A corpus unit re-runs on any change in its declared types.* That is the
  plan's rule and it makes =document_index= run on every edit. A corpus codec
  that is expensive will want the map and merge form.
- *Either files or diagnostics.* The story says so and the types enforce it.
  Code generation will meet models it cannot generate from. Whether that is a
  paired check codec or a third output kind is open.
- *Severity.* It is a column each codec fills. Ratchet mode may make it
  redundant, or configuration may want to set it per rule.
- *Corpus codecs are single pieces.* =document_index= bounds the wall time of
  a run at 11 ms on ORE Studio. A corpus codec that is expensive will need
  its own threads or the map and merge form.
- *Strings for options.* A mistyped value is found when the codec parses it,
  not when the registry is built. A declared value kind per option would move
  that check to the registry.
- *The =codecs= stage loads the corpus with its own code.* It repeats about
  sixty lines of the =warm= stage, which measures its phases apart and keeps
  nothing mapped. The real host should own one loader.
- *Stat data stands for content.* A tool that rewrites a generated file
  with the same size and restores its times and inode would go unnoticed,
  as it would by git. The racy rule covers the same-second case only.
- *Diff placement among repeated lines.* The diff is minimal but does not
  reproduce git's slider and indent heuristics, so a change among repeated
  lines may be shown in another, equally short place than git shows it.
- *Unregistered input types run anyway.* A codec that lists a type the
  registry lacks runs over the rest and the registry reports a problem. A
  host may prefer to refuse to run.
