* Goal

A scan stores each file's fact and findings once, where every worktree and
every later run finds them, and its result object no longer holds every
file the codec covers. On 2026-11-20 a scan's result was 87 to 100% scan
table, 1 to 9 MB, written again after any edit:
[[id:EDCF07F7-7981-4BF8-B908-8DD4E6D9121F][Why the result cache grows]].

* Acceptance

- A scan unit's result holds no per-file entries: its size does not grow
  with the number of files the codec covers.
- An edit to one file writes that file's fact object and the unit's result
  and manifest, nothing for the other files.
- A second worktree on the same content maps no file a first one mapped.
- The incremental behaviour of =ops_scan_tests.cpp= holds: only edited
  files are mapped, and the reduce step runs only when what it saw changed.
- Collection keeps the fact objects of every file a live record's scan
  units read.

* Plan

- *A fact object per file.* An action object of kind result under
  =scan_fact_key(codec, version, configuration, path, content)=: the SHA-1
  of those, so it names exactly what the map step's output depends on. Its
  body is the fact and the file's findings, encoded as now. The path is in
  the key because findings name their file.
- *The scan table shrinks* to what the reduce step needs to be skipped:
  the number of files, a digest of the (path, fact) pairs it reduced, in
  the order the codec listed them, the paths it read itself, and its
  findings.
- *A run* looks each listed file's fact object up by its key. A hit is used
  as the old table's entry was: logged as a file input, its findings
  reported. A miss is mapped, and its fact object is handed to the store
  with the unit's result. The reduce step is skipped when the digest and
  the count match the seed's and every other input of the last call holds,
  the files the reduce step read included. That is what
  =reduces_the_same= checks today, by comparing each remapped file's fact.
- *store_actions* writes the fact objects a run made, in the same pack.
- *Collection*: =action_keys= adds, for each unit of a record, the fact key
  of each file input. A unit's file inputs are the files it read or took
  from the cache, so the key of every fact a live scan uses is among them;
  keys of files that are no scan's name nothing, and keep nothing.
- The result format's version goes up, so an old table is not read as a
  new one; the first run after the change maps every file once.

* Notes

- The scan tables went from 1 to 9 MB to a few hundred bytes, and the
  results of an edit from 32 MB to 5 KB. What an edit still writes is
  manifests: a corpus unit's manifest keeps its last eight input sets, and
  each set lists every file the unit read, so each edit rewrites a manifest
  of up to 5.7 MB. That is [[id:8066E3E8-998F-4405-998E-1C1432B90800][Keep manifests small]].
- A second worktree maps only what no worktree mapped before, so its first
  run took half the time.
- The first run of this build maps every file of every scan once, since a
  table of the old format does not decode as a seed.
